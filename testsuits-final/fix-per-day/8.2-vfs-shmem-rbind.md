# 8-2 VFS 统一路径对象：shmem、递归绑定挂载与 mount graph

## 问题概述

旧实现把"路径字符串"当成文件的身份证。一旦文件被 rename、目录被 bind mount、
或者 mount 被覆盖，同一个字符串可能指向完全不同的文件，同一个文件也可能换了
路径——字符串就不再可靠了。shmem、递归绑定挂载、openat2、cgroup2、fanotify、
打开文件和进程 cwd 都受此影响。

```text
路径字符串 "/tmp/foo"
       │ 旧实现：规范化后当 key
       ▼
rename / bind-mount / overmount 之后
原字符串指向别的对象，或者对象换了路径但仍是同一个
       │
       ▼
stat() 与 fstat() 得到不同 st_dev，zombie 仍持有 cwd 导致 umount 失败
```

根因：路径解析的结果必须是真实的 (mount, dentry) 对象引用，不能是一段可以
被别人改掉含义的字符串。

## 背景知识

这一节给只上过操作系统课的读者铺路。已经熟悉 VFS 和 mount 的可以跳过。

**VFS 是什么**。Linux 把"文件系统"分成两层：上面是 VFS（Virtual File System，
虚拟文件系统），下面是具体的 ext4、tmpfs、procfs 等。VFS 提供统一接口——
`open`、`read`、`write`、`stat` 这些系统调用只跟 VFS 打交道，不需要知道底下是
磁盘文件系统还是内存文件系统。你可以把 VFS 理解成一个"转接头"：

```text
用户程序
   │  open("/tmp/foo", O_RDONLY)
   ▼
 VFS 层（统一接口）
   │  根据路径找到对应的 mount + dentry
   ▼
具体文件系统（ext4?  tmpfs?  procfs?）
   │  真正读数据
   ▼
块设备 / 内存 / 内核生成
```

VFS 里有三个核心对象：
- inode（索引节点）：代表一个文件或目录的元数据——权限、大小、时间戳。
- dentry（directory entry，目录项缓存节点）：代表"路径的一个分量"，
  比如 `/tmp/foo` 拆成 `/`、`tmp`、`foo` 三个 dentry。查找路径时逐级往下走。
- vfsmount（挂载实例）：代表"某个文件系统挂到了目录树的哪个位置"。

**mount 树怎么组织**。整个目录树不是一棵单纯的 dentry 树，而是一棵由 mount
拼起来的树。每次挂载都是在某个 dentry 上"盖"一个新文件系统，走路径时如果
踩到一个 mountpoint，VFS 就跳到盖在上面的那个文件系统的根 dentry 继续往下走。
所以同一个目录节点可以被多次挂载覆盖（overmount），也可以在不同路径出现。

**bind mount 和 rbind 的区别**。普通挂载是把一个块设备的文件系统挂到某个目录。
bind mount 不涉及新设备——它把一棵已有的目录树"再挂一份"到另一个位置：

```text
bind mount：只克隆根挂载
  /mnt/a  ──bind──▶  /mnt/b
  （/mnt/a 下面如果还挂了子文件系统，不会跟过去）

rbind (recursive bind)：递归克隆整棵子树
  /mnt/a  ──rbind──▶  /mnt/b
  （/mnt/a 下面所有已挂载的子文件系统一起复制到 /mnt/b 下对应位置）
```

为什么同一个目录能出现在多个路径下？因为 bind mount 创建的是一个新的 mount
对象，它共享源文件系统的 dentry 和 inode，但有自己的 mount ID。对内核来说
两者指向同一份数据，但路径解析经过不同 mount 到达。容器和 chroot 大量使用这个
机制来组装"看起来独立"的文件系统视图。

**tmpfs/shmem 为什么直接拿 page cache 当存储**。普通文件系统（ext4）的数据最终
要写到磁盘上，page cache（页缓存）只是加速层——读过的磁盘块留在内存里以备下次
用。但 tmpfs 没有后备磁盘，它的数据只存在于内存：page cache 本身就是最终存储。
写入一个 tmpfs 文件就是往 page cache 里写一页，不需要任何块 I/O。这也是为什么
`/dev/shm`（POSIX 共享内存）和 `memfd_create()`（匿名内存文件）都跑在 tmpfs
上面——它们需要的就是"一块有文件接口的内存"。内核内部把这套实现叫 shmem。

**为什么路径字符串不能当对象身份**。当文件被 rename、目录被 bind mount、或者
mount 被 overmount 之后，同一个路径字符串可能指向完全不同的对象，也可能同一个
对象有了另一个路径。真正不会变的身份是 (mount, dentry) 这个二元组——Linux 里的
`struct path { vfsmount, dentry }`。本文要解决的就是这个问题：把旧实现里到处
依赖路径字符串的做法，换成依赖真正的 VFS 对象。

## 如何发现

先用 `rg` 建立旧兼容层调用图，再以每组最小用户回归逐步删除调用者。代表性命令：

```sh
rg -n 'open_pseudo|AtPath::Ext4|AtPath::Vfs|RelativeAtPathBase|file_binds' os/src
rg -n 'VfsPath|PinnedPath|VfsMountNamespace|PathWalker|object_path' os/src/fs
```

代表性日志：173928 日志复现 `stat()`/`fstat()` 的 `st_dev` 不一致；224503 日志显示
zombie 仍持有 cwd 导致卸载语义错误。完整日志列表见存档 5.1--5.16。

## 怎么解决

**统一路径对象**：引入 `VfsPath { mount, dentry }` 和 `PinnedPath`（持有引用计数，
保证 mount 和 dentry 不会被提前释放）。路径查找上下文 `AtPath` 简化为
`{ namespace, root, start, path }`——绝对路径从进程 root 开始，相对路径从 cwd 或
dirfd 的 `f_path` 开始，同一 `PathWalker` 逐分量处理符号链接和跨 mount。ext4 只在
适配边界取 inode，不再另走字符串 walker。

**shmem / memfd**：memfd 和 `/dev/shm` 共享同一个内部 shmem mount 和 `shmem_id`；
`/proc/<pid>/fd/<n>` 的 magic link 直接返回打开文件的 `VfsPath`，不再把路径
字符串展开后重新解析。

**递归 bind**：普通 bind 只克隆根 mount 一个；`MS_BIND|MS_REC` 递归克隆整棵子树，
跳过 unbindable 分支。每个克隆 mount 拿到新 ID，共享源文件系统的 dentry。
mount 传播按父 mount 的 peer/slave 关系和被覆盖的 dentry 计算；卸载传播不会误删
不同父传播域下的副本。

**打开文件持有路径**：`File` 自身持有 `PinnedPath`，dup/fork 共享同一
`Arc<File>`，fd table 不再另外保存 mount 引用。

**现代 mount API**：`fsopen/fsconfig/fsmount/open_tree/move_mount` 只创建或移动
真实 mount 对象；`mount_setattr()` 同时提交 flags 和 propagation。readonly/nodev/
noexec/nosymfollow 从解析所得 mount 的 `VfsMountFlags` 读取。

**openat2**：`RESOLVE_BENEATH/IN_ROOT/NO_XDEV/NO_MAGICLINKS/NO_SYMLINKS` 进入同一
walker；未知 flag 位和扩展字段返回精确 Linux 错误码。

**zombie 退出前释放 FsStruct**：进程在变成 zombie 前先分离 cwd/root 的 path 引用，
未 reap 的 PCB 不再制造虚假的 mount busy。

Linux 参考：`struct path { vfsmount, dentry }`、`struct file::f_path`、namei 路径
查找、`copy_tree()` 递归克隆、mount propagation、`exit_fs()` 和 proc magic link。
CongCore 没有 RCU 路径遍历和完整 dcache，用引用计数加锁的方式做路径查找；
对象身份判定和发布顺序与 Linux 一致。
