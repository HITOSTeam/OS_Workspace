# 7-31 参考 Linux 拆除 ext4 与块 I/O 全局串行路径

## 问题概述

iozone 吞吐远低于预期，怀疑文件系统这条路上锁竞争很重。一次读写要连着穿过三层锁：

```text
全局 EXT4_LOCK
       ↓
持有 BLOCK_CACHE_MANAGER 等待磁盘
       ↓
VirtIO 请求同步提交并持续自旋
```

这三层锁是怎么叠起来的，`7-30-ext4.md` 已经写过，本文是对应的修改。

## 背景知识


**块缓存是什么**。磁盘按扇区读写，一次最小几百字节到几 KiB，而且延迟远高于内存。
所以文件系统在内存里留一块区域，把最近读过的磁盘块存起来，下次要同一块就直接给
内存里的副本，这就是块缓存。课上讲的「buffer cache」就是它。本项目的块缓存以
4 KiB 为一块，用一个哈希表按块号索引，再配一个 LRU 链表决定内存不够时先丢谁。

写入时不会立刻落盘，而是先改内存副本并打上 dirty（脏）标记，等到淘汰或者
`sync` 时再写回磁盘。这样能把多次小写合并成一次，但也带来一个并发问题：写回
过程要花很长时间（一次磁盘 I/O），期间别人可能又改了同一块。

**VirtIO 块设备怎么工作**。虚拟机里的磁盘不是真磁盘，而是宿主机模拟的。guest
和宿主之间靠一段共享内存通信，这段内存组织成两个环形数组：

```text
descriptor 表   ：每项描述一段缓冲区（物理地址 + 长度 + 读写方向）
avail ring      ：guest 往里放「这个请求我准备好了，你处理吧」
used ring       ：设备处理完往里放「这个请求做完了」
```

guest 填好 descriptor，把编号（叫 token）写进 avail ring，然后写一下设备寄存器
通知它（叫 kick）。设备做完后把 token 写进 used ring，并发一个中断。guest 在中断
里从 used ring 取回 token，就知道哪个请求完成了。

关键点是：avail ring 里可以同时放多个请求，设备也允许乱序完成。也就是说硬件本来
就支持「一次发好几个请求」，但如果软件写成「发一个、等它完成、再发下一个」，这个
能力就完全浪费了。旧代码就是这样，而且等待方式是死循环查看有没有完成：

```rust
while !self.can_pop() {
    spin_loop();      // 一直占着 CPU 什么也不干
}
```

**为什么锁的粒度决定并发度**。一把锁保护的范围越大，同时能干活的核就越少。如果
所有文件操作都要先抢同一把锁，那么八个核里最多一个核在干文件系统的活，另外七个
在排队，加核不加速。把锁按对象拆开（每个文件一把），访问不同文件的核就能同时进行。
这是本文所有修改的共同思路。

**中断处理里为什么要关中断**。VirtIO 完成是在硬件中断里处理的。假设普通代码正拿着
某把自旋锁，这时同一个核上来了中断，中断处理程序也要拿这把锁——普通代码被打断了，
没机会释放锁，中断又在死等，这个核就永久卡住了。解决办法是：凡是中断处理程序也会
碰的锁，普通代码拿它之前必须先关掉本核中断。Linux 里叫 `spin_lock_irqsave()`，
本文对应的是 `LocalIrqSaveGuard`。

**iozone 是什么**。一个文件 I/O 基准测试工具。`-t 4` 表示开 4 个进程同时读写，
`-i 0/1/2` 分别选顺序写、顺序读、随机读写，`-r 1k` 是每次读写 1 KiB，
`-s 4m` 是每个进程操作一个 4 MiB 的文件。它会分别报告首次写、重写、读、重复读等
阶段的吞吐，正好能区分「缓存命中路径快不快」和「真正落盘路径快不快」。

## 怎么解决

三层各拆一次，并且不新增所有人都要抢的锁。

**inode 层**：把全局 `EXT4_LOCK` 换成按 `(device_id, inode_num)` 查表取到的读写锁。这个
编号不会随路径写法或对象重建而变，所以同一个磁盘 inode 的多个 Rust 对象一定拿到同一把
锁。要改多个 inode 时按这个编号从小到大依次加锁，避免两个任务反向加锁互相等；跨目录
rename 再多取一把目录树锁。

### 1. 锁本身

改动前 `os/src/fs/inode.rs`——一把全局自旋+让出的互斥锁，所有 hart、所有 ext4 实例、所有 inode 共用：

```rust
struct Ext4Lock {
    held: AtomicBool,
}

impl Ext4Lock {
    fn lock(&self) {
        loop {
            if self.held
                .compare_exchange_weak(false, true, Ordering::Acquire, Ordering::Relaxed)
                .is_ok()
            {
                return;
            }
            spin_loop();
            if crate::task::processor::current_task().is_some() {
                crate::task::processor::suspend_current_and_run_next();
            }
        }
    }
    fn unlock(&self) { self.held.store(false, Ordering::Release); }
}

lazy_static! {
    static ref EXT4_LOCK: Arc<Ext4Lock> = Arc::new(Ext4Lock::new());
}

pub(crate) fn ext4_lock() -> Ext4Guard {
    let lock = Arc::clone(&EXT4_LOCK);
    lock.lock();
    Ext4Guard { lock }
}
```

改动后——按 `(device_id, inode_num)` 查表取读写信号量，外加一把只在跨目录 rename 时使用的拓扑锁：

```rust
lazy_static! {
    /// Linux `s_vfs_rename_mutex` analogue.  It is only taken for operations
    /// that move names between two directories, before either parent lock.
    static ref EXT4_TOPOLOGY_LOCK: KernelMutex<()> = KernelMutex::new(());
    /// Stable Linux `i_rwsem` equivalents.  ext4-fs may construct more than
    /// one Rust `Inode` object for the same on-disk inode (in particular for
    /// hard links), so object addresses cannot identify the lock.
    static ref EXT4_INODE_LOCKS:
        Mutex<BTreeMap<(usize, u32), Weak<Ext4InodeLock>>> =
        Mutex::new(BTreeMap::new());
}

pub(crate) struct Ext4InodeLock {
    semaphore: KernelRwSemaphore<()>,
    namespace_generation: AtomicUsize,
}

pub(crate) fn ext4_inode_key(inode: &Inode) -> (usize, u32) {
    (inode.device_id(), inode.inode_num())
}

fn ext4_inode_lock_by_key(key: (usize, u32)) -> Arc<Ext4InodeLock> {
    let mut locks = EXT4_INODE_LOCKS.lock();
    if let Some(lock) = locks.get(&key).and_then(Weak::upgrade) {
        return lock;
    }
    if locks.len() >= EXT4_INODE_LOCK_CACHE_MAX {
        locks.retain(|_, lock| lock.strong_count() != 0);
    }
    let lock = Arc::new(Ext4InodeLock::new());
    locks.insert(key, Arc::downgrade(&lock));
    lock
}
```

表本身仍有一把短锁，但它只覆盖一次 `BTreeMap` 查找，不覆盖任何磁盘输入输出，所以不是原来那种"整个文件系统操作串行化"的锁。`Weak` 存储让关闭和 unlink 后的 inode 能被回收，`EXT4_INODE_LOCK_CACHE_MAX = 4096` 触发一次惰性清理。

### 2. 单 inode 调用点

`stat_utils.rs` 的真实 diff，最典型的形态：

```diff
-    let meta = {
-        let _ext4_guard = ext4_lock();
-        inode.stat_snapshot()
-    };
+    let meta = with_ext4_inode_read(&inode, || inode.stat_snapshot());
```

```diff
-    let (inode, meta) = {
-        let _ext4_guard = ext4_lock();
-        let inode = resolve_at_inode(&at, fsuid, fsgid, true)?;
-        let meta = inode.stat_snapshot();
-        (inode, meta)
-    };
+    let inode = resolve_at_inode(&at, fsuid, fsgid, true)?;
+    let meta = with_ext4_inode_read(&inode, || inode.stat_snapshot());
```

两点变化：一是锁粒度从全局降到单个 inode；二是路径解析（`resolve_at_inode`，可能读多个目录块）被移出了临界区。读侧用 `read()` 共享，多个 hart `stat` 同一个文件也能并行。

### 3. 多 inode：按编号排序加锁

新增的辅助函数，就是你描述的"从小到大依次加锁"：

```rust
pub(crate) fn with_ext4_inode_write_set<R>(inodes: &[&Inode], operation: impl FnOnce() -> R) -> R {
    let mut locks = inodes
        .iter()
        .map(|inode| (ext4_inode_key(inode), ext4_inode_lock(inode)))
        .collect::<Vec<_>>();
    locks.sort_unstable_by_key(|(key, _)| *key);
    locks.dedup_by_key(|(key, _)| *key);
    let _guards = locks
        .iter()
        .map(|(_, lock)| lock.write())
        .collect::<Vec<_>>();
    operation()
}
```

`dedup_by_key(连续项目去重)` 不是可选的：同目录 rename 时两个 parent 是同一个 inode，读写信号量重复获取会自死锁。这也是必须用稳定编号而不是 `Arc` 地址做 key 的原因——同一个磁盘 inode 的两个 Rust 对象地址不同，去重会失效。

### 4. rename

`rename` 是改名字的系统调用，形式是 `rename(旧路径, 新路径)`。`mv` 命令底层就调它。

关键点：文件名不住在文件里，文件名住在**目录**里。目录本质上是一张表，记录"名字 → inode 编号"的对应关系。所以改名字这件事，改的是目录里的表项，不是文件本身。

由此就分出两种情况。

## 同目录（不跨）

```sh
mv /home/a.txt /home/b.txt
```

`a.txt` 和 `b.txt` 都住在 `/home` 这一张表里。内核要做的事就是把 `/home` 这张表里的一条记录改个名：

```
/home 目录:                    /home 目录:
  "a.txt" → inode 42     ──→     "b.txt" → inode 42
  "c.txt" → inode 43            "c.txt" → inode 43
```

只动了一个目录。inode 42 自己完全没变，文件内容、大小、权限都不动。

## 跨目录

```sh
mv /home/a.txt /tmp/a.txt
```

现在要动**两张表**：从 `/home` 里删掉一条，往 `/tmp` 里加一条。

```
/home 目录:                    /home 目录:
  "a.txt" → inode 42     ──→     "c.txt" → inode 43
  "c.txt" → inode 43

/tmp 目录:                     /tmp 目录:
  "x"     → inode 88     ──→     "x"     → inode 88
                                 "a.txt" → inode 42
```

而且这两步必须是**原子**的——不能出现"两个目录里都有"或者"两个目录里都没有"的中间状态被别人看到，否则文件就凭空多出来或者丢了。

如果被移动的东西是个**目录**，还要多改两处：这个目录里的 `..` 项要从指向旧父目录改成指向新父目录；旧父目录和新父目录的链接计数（`nlink`）要一减一加。所以跨目录移动一个目录，最多要同时修改四个 inode。

## 判据是父目录，不是路径字符串

"跨路径"这个说法容易误导。真正的判据不是两个路径字符串长得不一样，而是**两个父目录是不是同一个 inode**。代码里就是这么写的：

```rust
let _topology_guard = (!inode_eq(&old_parent, &new_parent)).then(ext4_topology_lock);
```

举几个例子:

| 操作 | 路径字符串 | 父目录 | 算跨吗 |
|---|---|---|---|
| `/home/a` → `/home/b` | 不同 | 都是 `/home` | 不跨 |
| `/home/a` → `/home/./b` | 差别更大 | 都是 `/home` | 不跨 |
| `/home/a` → `/tmp/../home/b` | 完全不同 | 都是 `/home` | 不跨 |
| `/home/a` → `/tmp/a` | 不同 | `/home` vs `/tmp` | 跨 |

所以必须先把路径解析成 inode，再比较，不能比字符串。第三行那个例子最能说明问题：`/tmp/../home` 化简之后就是 `/home`，字符串比较会误判成跨目录。

## 为什么它需要那把额外的锁

回到上一轮说的死锁问题。同目录改名只锁一个目录，不可能和别人交叉。跨目录改名要锁两个目录再加子对象，而"父"和"子"的角色是相对的——同一个目录 `y`，在"把 `y` 搬走"这个操作里是被锁的子对象，在"往 `y` 里搬东西"这个操作里是父目录。两个操作对它的角色认知相反，加锁顺序就可能反过来，绕成环。

所以只有跨目录的情况才去取那把目录树锁，把这类操作排成一队。跨目录移动本来就不频繁，串行化不心疼；而占绝大多数的同目录改名，以及不同目录里各自的改名，完全不受影响，照样并行。

## 一个相关的限制

`rename` 不能跨**文件系统**。把文件从一块盘挪到另一块盘，内核会返回 `EXDEV` 错误，因为 inode 编号只在自己的文件系统内有效，没法让另一个文件系统的目录去引用它。这时 `mv` 命令会自己退化成"完整复制一份 + 删除原件"——这也是为什么 `mv` 在同一分区内瞬间完成，跨分区却要等半天。

改动前，整个 `do_renameat` 在一把全局锁下：

```rust
    let _ext4_guard = ext4_lock();
    let (fsuid, fsgid) = current_fsuid_gid();
    let (old_parent, old_name) = match resolve_parent_and_name(&old_at, fsuid, fsgid) { ... };
    let (new_parent, new_name) = match resolve_parent_and_name(&new_at, fsuid, fsgid) { ... };

    if old_name.is_empty() || new_name.is_empty() { ... }
```

改动后，拓扑锁 → 父目录集合 → 子对象集合，三层嵌套：

```rust
    // topo lock 
    let _topology_guard = (!inode_eq(&old_parent, &new_parent)).then(ext4_topology_lock);

    with_ext4_inode_write_set(&[old_parent.as_ref(), new_parent.as_ref()], || {
        ...
        // Do this before taking child locks: `new_parent` can itself be the
        // source directory for `rename("a", "a/b")`, in which case nesting
        // the source i_rwsem below would recursively lock a parent semaphore.
        if source.is_dir() && path_is_descendant_of(new_parent.clone(), &source) {
            return err(SyscallError::EINVAL);
        }

        let mut changed_inodes = vec![source.as_ref()];
        if let Some(target_inode) = target.as_ref() {
            changed_inodes.push(target_inode.as_ref());
        }
        with_ext4_inode_write_set(&changed_inodes, || { ... })
    })
```

`.then(ext4_topology_lock)` 让同目录 rename 完全绕过拓扑锁——这是有意的，也是正确的：父集合本身按编号全局排序，父与父之间不会反向；父→子方向沿目录树单向，树无环所以也不会成环；唯一能构造出"A 的子是 B 的父"这种反转的场景就是跨目录移动，而那些全被拓扑锁串起来了。这跟 Linux 只在 `!= old_dir` 时取 `s_vfs_rename_mutex` 的判据一致。

---

块缓存的代码在 `ext4-fs/src/block_cache.rs`，改动是两个提交：`53368b5d`（把输入输出移出 manager 锁）和 `c948a928`（限制回收扫描）。

## 先说清楚这一层是干什么的

磁盘按块读写，这个文件系统里一块是 4 KiB。每次访问文件都去读盘太慢，所以内存里留一份副本，这就是块缓存。它是一张表：块号 → 内存里那份数据。

```rust
pub struct BlockCacheManager {
    entries: CacheEntryMap,          // 块号 → 缓存
    queue: VecDeque<(CacheKey, u64)>, // 用于决定内存满了淘汰谁
    stamp: u64,
}
```

这张表是所有 CPU 共享的，所以要加锁。问题出在**锁住的时间有多长**。

## 改动前：拿着锁去读盘

```rust
pub fn get_block_cache(
    block_id: usize,
    block_device: Arc<dyn BlockDevice>,
) -> Arc<Mutex<BlockCache>> {
    let mut manager = BLOCK_CACHE_MANAGER.lock();   // 拿锁
    manager.get_block_cache(block_id, block_device) // 整个过程都在锁里
}
```

`manager.get_block_cache` 内部，命中就直接返回；没命中就调 `load_block_range`：

```rust
fn load_block_range(&mut self, block_device: ..., start_block: usize, count: usize)
    -> Arc<Mutex<BlockCache>>
{
    let mut buf = vec![0u8; count * BLOCK_SZ];
    block_device.read_blocks(start_block, &mut buf);   // ← 真的去读磁盘，锁还在手里
    ...
        self.ensure_capacity();                        // ← 内存满了在这里淘汰
    ...
}
```

问题就在这一行 `read_blocks`。读一次磁盘要几十微秒到几毫秒，这段时间锁一直被占着。后果是：另一个 CPU 想访问一个**本来就在内存里**的块，明明零成本就能拿到，也得排在这次读盘后面。缓存命中被磁盘等待拖累，这是最亏的一种。

淘汰更隐蔽。内存满了要腾位置：

```rust
fn ensure_capacity(&mut self) {
    while self.entries.len() >= BLOCK_CACHE_SIZE {
        self.evict_one();
    }
}

fn evict_one(&mut self) {
    while let Some((key, stamp)) = self.queue.pop_front() {
        if let Some(entry) = self.entries.get(&key) {
            if entry.stamp == stamp && Arc::strong_count(&entry.cache) == 1 {
                self.entries.remove(&key);    // 看起来只是删表项
                return;
            }
        }
        ...
    }
    panic!("Run out of BlockCache!");
}
```

`self.entries.remove(&key)` 看着只是删一条记录，但被删掉的缓存有这个：

```rust
impl Drop for BlockCache {
    fn drop(&mut self) {
        self.sync()      // 里面是 write_block()，写磁盘
    }
}
```

也就是说淘汰一个改过的块，会在 `remove` 那一刻**触发一次写盘**，而这一刻仍然在 manager 锁里面。写盘藏在 `Drop` 里，看代码完全看不出来这里有输入输出。这类隐式副作用是最难查的性能问题。

`block_cache_sync_all()`（把所有脏数据刷回磁盘，`sync` 系统调用会走到）同样是全程持锁：

```rust
pub fn block_cache_sync_all() {
    let manager = BLOCK_CACHE_MANAGER.lock();
    for entry in manager.entries.values() {
        entry.cache.lock().sync();       // 逐个写盘，锁全程不放
    }
}
```

刷盘期间整个文件系统停摆。

## 改动后：先占位，再读盘

核心思路是把"一次缺失处理"拆成两段：**在锁里决定要做什么**，**出了锁再去做**。

第一步是给表项加一个新状态。原来表里只能存"已就绪的缓存"，现在多了一个"正在读取中":

```rust
enum CacheSlot {
    Loading(LoadingEntry),   // 位置已占住，数据还在路上
    Ready(CacheEntry),       // 数据已就绪
}

struct LoadState {
    done: AtomicBool,        // 读完了没有
}

struct LoadingEntry {
    state: Arc<LoadState>,
    block_device: Arc<dyn BlockDevice>,
}
```

第二步，锁里的函数不再直接干活，而是返回一张"待办单":

```rust
enum CacheLookup {
    Ready(Arc<Mutex<BlockCache>>),   // 命中，直接用
    Created(Arc<Mutex<BlockCache>>), // 新建的空白块
    Wait(Arc<LoadState>),            // 别人在读同一块，等他
    Load(LoadTicket),                // 归你读，凭单子去读
    Evict(EvictionTicket),           // 内存满了，先把这块清出去
    Retry,                           // 暂时没法处理，稍后重来
}
```

第三步，外层是一个循环，反复"进锁拿待办单 → 出锁执行"：

```rust
pub(crate) fn get_block_cache_with_hint(
    block_id: usize,
    block_device: Arc<dyn BlockDevice>,
    read_ahead: usize,
) -> Arc<Mutex<BlockCache>> {
    loop {
        let action = {
            let mut manager = BLOCK_CACHE_MANAGER.lock();
            manager.prepare_load(Arc::clone(&block_device), block_id, read_ahead)
        };                                    // ← 锁在这里就放掉了

        // 读到是一个action 
        match action {
            CacheLookup::Ready(cache) => return cache,
            CacheLookup::Created(cache) => return cache,

            CacheLookup::Wait(state) => wait_for_load(&state, &block_device),

            CacheLookup::Load(ticket) => {
                let mut buf = vec![0u8; ticket.count * BLOCK_SZ];
                ticket.block_device.read_blocks(ticket.start_block, &mut buf);  // 锁外读盘
                // ... 把 buf 切成一个个 BlockCache ...
                let cache = {
                    let mut manager = BLOCK_CACHE_MANAGER.lock();   // 重新拿锁，只为登记
                    manager.publish_load(&ticket, loaded)
                };
                return cache;
            }

            CacheLookup::Evict(ticket) => sync_eviction(ticket),
            CacheLookup::Retry => block_device.io_relax(),
        }
    }
}
```

对比一下就能看出来：manager 锁现在只出现在两个花括号块里，中间那句 `read_blocks` 完全在锁外。

淘汰也是同样的拆法，写盘在锁外，写完再进锁确认删除：

```rust
fn sync_eviction(ticket: EvictionTicket) {
    sync_block_cache(&ticket.cache);              // 锁外写盘
    {
        let mut manager = BLOCK_CACHE_MANAGER.lock();
        manager.finish_eviction(&ticket);         // 锁内只做登记

}
```

`sync_all` 改成先在锁里拍一张快照，出锁再逐个写：

```rust
pub fn block_cache_sync_all() {
    loop {
        let (ready, loading) = {
            let manager = BLOCK_CACHE_MANAGER.lock();
            manager.snapshots()                   // 只是复制一堆 Arc，很快
        };
        if !loading.is_empty() {
            for (state, block_device) in loading {
                wait_for_load(&state, &block_device);   // 等还在读的那些完成
            }
            continue;
        }
        let targets = ready.into_iter()
            .map(|cache| { let target = cache.lock().writeback_target(); (cache, target) })
            .collect::<Vec<_>>();
        for (cache, target) in targets {
            sync_cache_through(&cache, target);   // 锁外写盘
        }
        return;
    }
}
```

## 为什么需要 Loading 这个中间状态

如果只是简单地"出锁读盘"，会出新问题：八个 CPU 同时发现块 7 不在缓存里，八个都出锁去读盘，同一块读八遍，还可能互相覆盖。

`Loading` 就是解决这个的。第一个发现缺失的任务在锁里**先把表项占住**，标记为"正在读取"：

```rust
let state = Arc::new(LoadState::new());
for key in missing_keys.iter().copied() {
    self.entries.insert(
        key,
        CacheSlot::Loading(LoadingEntry {
            state: Arc::clone(&state),
            block_device: Arc::clone(&block_device),
        }),
    );
}
CacheLookup::Load(LoadTicket { start_block, count, state, block_device, reserved_keys })
```

后来的任务查表时看到的不是"没有"，而是"有，但正在读"，于是拿到 `Wait`：

```rust
Some(CacheSlot::Loading(entry)) => Some(CacheLookup::Wait(Arc::clone(&entry.state))),
```

然后等着，不重复发请求：

```rust
fn wait_for_load(state: &LoadState, block_device: &Arc<dyn BlockDevice>) {
    while !state.is_done() {
        block_device.io_relax();      // 让出 CPU，不空转
    }
}
```

读完的那个任务把数据登记进表，并通知等待者：

```rust
fn publish_load(&mut self, ticket: &LoadTicket, mut loaded: Vec<...>) -> Arc<Mutex<BlockCache>> {
    loaded.reverse();
    for (key, cache) in loaded {
        let owns_slot = matches!(
            self.entries.get(&key),
            Some(CacheSlot::Loading(entry)) if Arc::ptr_eq(&entry.state, &ticket.state)
        );
        if !owns_slot { continue; }        // 这个位置已经被别人接管，不要动
        self.insert_ready(key, cache);
    }
    ...
    ticket.state.finish();                 // 唤醒所有等待者
    requested
}
```

这个模式有个名字叫 **single-flight**：同一份工作只做一次，其余人共享结果。有测试专门验证：

```rust

    ...
    assert!(Arc::ptr_eq(&first, &second));                          // 两个线程拿到同一个对象
    assert_eq!(device.read_operations.load(Ordering::Relaxed), 1);  // 磁盘只读了一次
    assert_eq!(cache_diagnostics().loads, 1);
}
```

## 版本号解决什么问题

一旦写盘挪到锁外，就出现一个新的正确性问题。原来的脏标记只是个布尔值：

```rust
// 改动前
modified: bool,

pub fn sync(&mut self) {
    if self.modified {
        self.modified = false;                             // 先清标记
        self.block_device.write_block(self.block_id, &self.cache);   // 再写盘
    }
}
```

设想这个时序：任务 A 决定回写，把内存里的数据复制出来准备写盘（此时数据是 `0xaa`）；写盘期间任务 B 把这个块改成了 `0xbb`；A 写完，清掉脏标记。结果磁盘上是 `0xaa`，内存里是 `0xbb`，而系统认为"已经落盘了"。`0xbb` 就丢了。

修法是把布尔值换成两个计数器：

```rust
/// Generation most recently modified in memory.
dirty_generation: u64,
/// Generation most recently written to the device.
synced_generation: u64,
/// Serialize writeback without holding the cache data lock across I/O.
writeback_in_progress: bool,
```

每次内存里被改动，`dirty_generation` 加一：

```rust
fn mark_dirty(&mut self) {
    self.dirty_generation = self.dirty_generation.saturating_add(1);
}
```

回写开始时，把当前版本号连同数据一起**拍快照**带走：

```rust
fn prepare_writeback(&mut self, target: u64) -> WritebackPreparation {
    if self.synced_generation >= target {
        return WritebackPreparation::Done;              // 已经落盘了，不用写
    }
    if self.writeback_in_progress {
        return WritebackPreparation::Busy(Arc::clone(&self.block_device));  // 别人在写，等
    }
    self.writeback_in_progress = true;
    WritebackPreparation::Ready(Writeback {
        generation: self.dirty_generation,              // 快照版本号
        block_id: self.block_id,
        block_device: Arc::clone(&self.block_device),
        data: self.cache.clone(),                       // 快照数据
    })
}

fn finish_writeback(&mut self, generation: u64) {
    self.synced_generation = self.synced_generation.max(generation);   // 只推进到快照那一版
    self.writeback_in_progress = false;
}

fn is_clean(&self) -> bool {
    self.synced_generation >= self.dirty_generation && !self.writeback_in_progress
}
```

回到刚才的时序：A 带走的快照版本号是 1；B 的写入把 `dirty_generation` 推到 2；A 写完只把 `synced_generation` 设成 1。于是 `is_clean()` 里 `1 >= 2` 不成立，块仍然是脏的，`0xbb` 会在下一次回写时落盘。

## 预读的边界

预读的意思是：既然已经付了一次寻址代价，顺手多读几块，赌接下来会用到。但不能乱读——读多了浪费带宽，读到不连续的位置就完全白费。

上限在 `ext4-fs/src/vfs.rs`：

```rust
const EXTENT_READ_AHEAD_BLOCKS: usize = 32;

fn extent_read_ahead_blocks(phys_off: usize, remaining: usize, block_size: usize) -> usize {
    phys_off
        .saturating_add(remaining)
        .div_ceil(block_size)
        .clamp(1, EXTENT_READ_AHEAD_BLOCKS)
}
```

`BLOCK_SZ` 是 4096，所以 32 块 = 128 KiB，这是你说的那个上限。

第二个约束是不跨 extent。ext4 用 extent 记录"这个文件的第 100 到第 200 个逻辑块，连续存在磁盘的第 5000 块开始处"。在一个 extent 内部，逻辑连续等于物理连续，一次请求就能读完；跨过 extent 边界，磁盘位置就跳走了，一次请求读不了。调用处的注释说明了这点：

```rust
while remaining > 0 {
    // `remaining` is already clipped to this extent, so the hint
    // never crosses a non-contiguous physical mapping.
    let read_ahead = extent_read_ahead_blocks(phys_off, remaining, block_size);
    let cache = get_block_cache_with_hint(cur_block, Arc::clone(&self.block_device), read_ahead);
```

`remaining` 在进入这个循环前已经被裁剪到当前 extent 之内，所以算出来的预读量天然不会越界。

顺带一提，改动前的预读量是 `READ_AHEAD_BLOCKS`，值是 1（LoongArch 上 2），基本等于没有预读——因为在旧结构下预读是持着 manager 锁做的，读得越多别人等得越久，不敢放大。把输入输出移出锁之后才有条件把它开到 128 KiB。这是两个改动之间的因果关系，不是两件独立的事。

还有一个安全性细节：预读时**绝不覆盖已存在的表项**。`prepare_load` 里只对 `missing_keys` 占位，`publish_load` 里再用 `owns_slot` 二次确认。否则一次投机性的预读可能把某个已经被改写、还没落盘的脏块用磁盘上的旧数据盖掉。测试 `read_ahead_batches_io_without_clobbering_dirty_cache` 就是防这个的。

## 一点补充：淘汰扫描的上限

`c948a928` 那个提交处理的是另一个相关问题。改动前的 `evict_one` 会一直扫到找到可淘汰的为止，最坏情况扫完整个队列，实在找不到就 `panic!("Run out of BlockCache!")`。缓存有一万多项时，这个扫描持锁时间不可控。

现在扫描窗口固定，而且优先挑干净的块（干净块不用写盘，淘汰成本为零）：

```rust
const CLEAN_RECLAIM_SCAN_LIMIT: usize = 64;

fn select_eviction(&mut self) -> Option<EvictionTicket> {
    // Linux's reclaim scanner gives clean file-cache pages preference, but
    // bounds each scan and falls back to writeback instead of holding an
    // LRU lock while walking an unbounded dirty set. ...
    let scan_limit = self.queue.len().min(CLEAN_RECLAIM_SCAN_LIMIT);
```

扫 64 项，有干净的就用；全是脏的就退化成回写最老的那个；一个都挑不出来（比如都正被别人使用）就返回 `None`，让调用方拿到 `Retry` 稍后重试，而不是崩溃。

**VirtIO 层**：每个 token 单独一个请求对象，请求没完成前调用者的缓冲区一直有效，因此
队列里可以同时挂多个请求，不必一个做完再发下一个。提交和硬中断里的完成处理用同一把
会关中断的队列锁；完成时回收 used ring、标记请求做完并唤醒等待的任务。调用者先轮询

## 1. 问题背景

此前的分析见 [7-30-ext4.md](./7-30-ext4.md)。当时已经定位到结构性问题，但
没有直接删除 `EXT4_LOCK`，因为它同时掩盖了 ext4 后端、路径查找、块缓存和
VirtIO 完成路径中的多个并发假设。

旧路径可简化为：

```text
hart 0: read("/work/a")
hart 1: create("/tmp/b")
hart 2: stat("/bin/c")
hart 3: readdir("/work")
                 │
                 ▼
          全局 EXT4_LOCK
       所有 ext4 实例共同竞争
                 │
                 ▼
       BLOCK_CACHE_MANAGER
      cache miss 时仍持有该锁
                 │
                 ▼
       VirtIO submit + spin
                 │
                 ▼
             used ring
```

这条路径存在三个不同层次的问题。

### 1.1 所有 inode 操作被一把锁覆盖

`EXT4_LOCK` 不区分：

- 读操作和写操作；
- 普通文件和目录；
- 不同 inode；
- 不同块设备上的 ext4 实例；
- 只访问缓存的操作和真正需要设备 I/O 的操作。

因此多核只能并行执行文件系统之外的计算。一旦进入 ext4，吞吐仍接近单通道。
把等待者从自旋改成 `yield` 只能降低等待时的 CPU 浪费，不能提高并发度。

### 1.2 cache miss 把无关缓存命中也挡在磁盘之后

旧 block cache manager 在持锁状态下完成：

```text
查找缓存
  ├─ hit  -> 返回
  └─ miss -> 分配 buffer
             -> read_block()
             -> 建立缓存项
             -> 返回
```

当一个冷块读取耗时较长时，另一个 hart 即使访问已经存在的热块，也无法进入
manager 查询。脏块淘汰和 `sync_all` 同样可能在 manager 锁内等待设备。

### 1.3 VirtIO 队列深度没有转化为并行能力

VirtQueue 本身支持多个 descriptor chain，但旧调用者提交一个请求后立即等待
对应 used element：

```text
submit token N
while token N 尚未完成:
    spin_loop()
pop token N
```

这会造成：

- 当前 hart 在设备延迟期间持续占用 CPU；
- 上层锁的持有时间覆盖完整设备等待；
- 队列虽然有多个槽位，但提交路径容易退化成一次只有一个有效请求；
- 完成、轮询和硬中断若使用不同锁域，容易产生 used ring 竞态；
- “检查条件后、真正阻塞前”可能发生完成，形成经典丢唤醒窗口。

## 3. 设计目标与非目标

### 3.1 目标

1. 删除所有 pathname syscall 对全局 `EXT4_LOCK` 的依赖。
2. 不同 inode 的只读操作可以并行。
3. 同一 inode 的 mutation 保持串行，读写之间保持一致性。
4. 多 inode 操作具有稳定锁序，不因对象地址或路径字符串变化而死锁。
5. cache miss、淘汰回写和 `sync_all` 不持有全局 manager 锁等待设备。
6. 同一个冷块只产生一次实际读取。
7. VirtIO 可保留多个在途请求，IRQ 和短轮询共用同一完成路径。
8. 不允许 DMA 在 syscall 返回后继续访问已经失效的调用者 buffer。
9. 队列满、短轮询耗尽和早期启动路径都能继续取得进展。
10. RISC-V 和 LoongArch 均能通过静态构建。

### 3.2 非目标

本批次不实现：

- Linux 完整 page cache；
- 后台 writeback thread；
- blk-mq 多硬件队列、tag set 和 request merge；
- 设备 reset、超时取消和错误恢复；
- ext4 journal；
- RCU pathwalk；
- 完整 VFS mount graph。

30 秒请求阈值目前只打印诊断。没有设备 reset 和 DMA 撤销机制时，不能为了返回
`ETIMEDOUT` 而释放仍由设备拥有的 buffer。

## 4. block cache：从锁内 I/O 改为两阶段状态机

相关文件：

- `ext4-fs/src/block_cache.rs`
- `ext4-fs/src/block_dev.rs`
- `ext4-fs/src/vfs.rs`

### 4.1 `Loading/Ready` single-flight

cache slot 不再只有“存在/不存在”，而是：

```text
Absent
  │
  │ 在 manager 锁内预留
  ▼
Loading(state)
  │
  │ 释放 manager 锁
  │ 执行 read_blocks()
  │
  ▼
Ready(cache)
```

第一个 miss 成为 loader：

1. 在 manager 锁内插入 `Loading`；
2. 释放 manager 锁；
3. 执行设备读取；
4. 重新取得 manager 锁；
5. 发布 `Ready` 并完成 `LoadState`。

并发访问同一 block 的其他 hart 看到 `Loading` 后不会重复提交读取，而是调用
`BlockDevice::io_relax()` 等待状态完成。内核块设备把这个 hook 实现为调度器
协作让出，host 单测中的默认实现则保留 `spin_loop()`。

关键效果是：一个冷块加载期间，其他缓存项仍可正常命中。

### 4.2 预读不会覆盖脏缓存

一次预读可能覆盖多个物理 block，但 manager 只为当前不存在的 key 建立
`Loading`。已经存在的 `Ready`，尤其是 dirty cache，不会被预读 buffer 覆盖。

发布前还会验证：

```text
当前 slot 仍是 Loading
并且 slot.state 与本次 LoadTicket.state 相同
```

因此过期 loader 不能覆盖后来建立的缓存项。

### 4.3 LRU 淘汰分成选择、回写和提交

淘汰不再在 manager 锁内直接 drop dirty cache，而是：

```text
manager lock:
    选择候选
    标记 evicting
    获取稳定 Arc
manager unlock

执行 generation-safe writeback

manager lock:
    验证 key / stamp / Arc / strong_count
    成功则删除
    失败则清除 evicting 并重新入队
manager unlock
```

验证失败时必须重新加入 LRU，否则一个并发重新引用过的 cache 可能永久失去淘汰
候选身份。

### 4.4 generation-safe writeback

单纯把 dirty bool 在 I/O 后清零存在竞态：

```text
CPU 0: 拷贝旧数据，开始写回 generation 7
CPU 1: 修改 cache，进入 generation 8
CPU 0: I/O 完成，错误地标记整个 cache clean
```

当前 `BlockCache` 保存：

```text
dirty_generation
synced_generation
writeback_in_progress
```

写回者先复制目标 generation 和数据，再释放 cache data lock 执行设备 I/O。
完成时只推进 `synced_generation` 到本次写出的 generation。如果等待期间出现新
写，`dirty_generation` 更大，后续仍会再次写回。

这同时满足两个要求：

- cache data lock 不覆盖设备延迟；
- 并发新写不会被旧写回误判为已同步。

### 4.5 `sync_all` 不再持有 manager 锁

`block_cache_sync_all()` 先在 manager 锁内拍摄 `Arc` 快照，然后释放 manager
锁，再逐项写回。如果快照中仍有 `Loading`，先等待加载完成并重新拍摄。

这与 Linux 把对象查找/固定和实际 writeback 分离的原则一致。

## 5. extent 内最多 128 KiB 的有界预读

旧代码以单个 4 KiB block 为单位读取。连续读取大文件时，每个 block 都产生
一次 cache lookup 和一次块请求。

当前 `ext4-fs/src/vfs.rs` 在已经解析出的 extent 内计算：

```text
read_ahead_blocks =
    ceil((physical_offset + remaining_in_extent) / 4 KiB)
    clamp 1..32
```

因此单次最多读取：

```text
32 × 4 KiB = 128 KiB
```

边界由当前 extent 的剩余长度约束，不会跨到下一个不连续 extent。它比 Linux
完整 readahead state machine 简单，但保留了两个关键原则：

- 窗口有上限；
- 只有已知物理连续的数据才合并。

## 6. inode 锁：从全局锁变为稳定对象锁

相关文件：

- `os/src/fs/inode.rs`
- `os/src/fs/ext4/mod.rs`
- `os/src/syscall/filesystem/*.rs`
- `os/src/syscall/memory/mmap.rs`
- `os/src/syscall/process/exec.rs`

### 6.1 为什么不能直接按 Rust 对象地址加锁

同一个磁盘 inode 可能因为：

- 多次 path lookup；
- hard link；
- 不同目录项；
- adapter 重新构造；

对应多个 Rust `Inode` 对象。若锁绑定对象地址，同一个磁盘 inode 会得到多把
锁，无法保护元数据。

当前使用：

```text
InodeLockKey = (device_id, inode_num)
```

这相当于 Linux 中 inode 对象的稳定身份。锁表保存
`Weak<KernelRwSemaphore<()>>`，活跃调用持有强引用；inode 关闭或删除后，失效
weak entry 可以被清理。

### 6.2 读写锁语义

典型映射为：

| 操作 | 锁 |
| --- | --- |
| metadata snapshot、普通读取、类型检查 | inode read |
| write、truncate、chmod/chown、xattr mutation | inode write |
| create、link、unlink | parent write，必要时 child write |
| rename/exchange | topology mutex + parent/child write set |
| exec、文件 mmap 建立 | inode read 或与 text-write 状态配合 |

新 `KernelRwSemaphore` 使用 writer preference：只要存在等待 writer，新 reader
就不能继续插队，避免持续读负载饿死 truncate、rename 或 metadata 更新。

### 6.3 多 inode 的固定锁序

`with_ext4_inode_write_set()` 会：

1. 取得每个 inode 的稳定 key 和锁对象；
2. 按 `(device_id, inode_num)` 排序；
3. 去除重复 inode；
4. 按排序结果逐个取得 write guard；
5. 执行 mutation。

这对应 Linux `lock_two_nondirectories()` 的固定顺序思想，但使用稳定磁盘 key，
而不是内存地址。

### 6.4 rename topology mutex

跨目录 rename 在父目录锁之前取得一个保守的 topology mutex，防止两个目录树
变更以相反顺序锁住祖先关系。

当前它比 Linux 的 per-superblock `s_vfs_rename_mutex` 更粗，因为仍是全局
topology mutex；但它只覆盖跨目录 rename，不覆盖普通 read/write/lookup。
后续 VFS 引入稳定 filesystem object 后，应把该锁移动到每个 filesystem
实例。

### 7.1 waitqueue 的经典丢唤醒窗口

错误顺序是：

```text
waiter                         waker
检查 condition = false
                               condition = true
                               wake: 队列为空
把自己加入队列
睡眠
```

当前顺序为：

```text
waiter:
    快速检查 condition
    irqsave
    取得 waitqueue lock
    再次检查 condition
    若仍为 false，入队
    释放 lock / 恢复 IRQ
    切换任务

waker:
    irqsave
    取得同一 waitqueue lock
    取出 waiter
    释放 lock / 恢复 IRQ
    wakeup_task()
```

第二次条件检查和 waker 的同一把 queue lock 共同关闭了 check-to-enqueue 窗口。

### 7.2 为什么 waitqueue 元数据锁必须 irq-save

VirtIO 完成可以在硬中断中调用 wake。如果普通内核上下文持有 waitqueue
spinlock 时被同一 hart 的硬中断打断，中断再次尝试取得该锁，就会永远自旋。

因此 waitqueue 和 VirtIO queue state 均使用 `LocalIrqSaveGuard`，对应 Linux
的 `spin_lock_irqsave()`。

## 8. `try_to_wake_up()` 风格的 `on_cpu` 交接

只修正 waitqueue 本身仍不够。CongCore 的任务切换有一个特殊阶段：

1. 任务决定阻塞；
2. 切到 idle；
3. idle 才清除旧任务的 `on_cpu`；
4. idle 再完成入队或 blocked 状态处理。

如果硬中断在 1 和 3 之间唤醒任务，waker 看到 `on_cpu != OFF_CPU`，只能设置
`wakeup_pending`。旧 idle 路径检查 pending 和清 `on_cpu` 不是一个原子决策，
仍可能丢失唤醒。

当前每个 TCB 增加 task-local wakeup transition lock：

```text
waker                         outgoing CPU / idle
irqsave                       IRQ 已关闭
lock transition              lock transition
检查 on_cpu                  clear on_cpu
设置 wakeup_pending          consume wakeup_pending
unlock                        unlock
```

内存序使用 acquire/release，作用对应 Linux `p->pi_lock` 与
`smp_cond_load_acquire(&p->on_cpu)` 的最小版本。

如果 waker 观察到任务仍在 CPU 上：

- 不直接把同一个内核栈重新入队；
- 设置 `wakeup_pending`；
- 由旧 CPU 切到 idle 并发布 `OFF_CPU` 后完成唤醒。

这保证同一任务不会同时在两个 hart 上运行。

## 9. VirtIO：分离提交、完成和调用者等待

相关文件：

- `os/src/drivers/block/async_queue.rs`
- `os/src/drivers/block/virtio_blk.rs`
- `os/src/drivers/block/mod.rs`
- `vendor/virtio-drivers-pci/src/device/blk.rs`
- `vendor/virtio-drivers-pci/src/queue.rs`

### 9.1 请求对象生命周期

每个请求保存：

```text
BlockRequest
├─ kind: Read / Write
├─ sector
├─ BlkReq
├─ data pointer + length
├─ BlkResp
├─ result / completed
├─ submit timestamp
└─ diagnostic state
```

请求表按 VirtQueue token 保存 `Arc<BlockRequest>`。只有 used ring 返回 token
后，完成路径才移除该表项。

调用者使用同步接口，因此在 `completed` 前不会返回、不会消费 fatal signal，
其 slice 生命周期覆盖整个 DMA 请求。这是 Linux bio pin 页面语义在当前内核中
的最小对应。

需要准确说明“zero-copy”的边界：本批次删除的是 `async_queue` 内每个请求额外
分配的 4 KiB 数据 buffer 和往返复制；具体 `Hal::share()` 仍可根据架构和地址
选择 direct DMA 或 bounce buffer，因此它不是所有架构上的端到端零复制。

### 9.2 多在途请求

队列最多跟踪 32 个请求，实际数量受设备报告的 VirtQueue size 限制：

```text
task A submit token 0 ─┐
task B submit token 3 ─┼─> device
task C submit token 5 ─┘

IRQ
 │
 ▼
drain used ring
 ├─ complete token 3
 ├─ complete token 0
 └─ complete token 5
```

完成顺序不要求与提交顺序一致。每个 token 对应独立请求对象。

### 9.3 提交和硬中断完成共享同一锁

Linux `virtio_queue_rq()` 与 `virtblk_done()` 使用同一 virtqueue lock。CongCore
同样在以下两条路径取同一个 `state` lock，并先关闭本地中断：

```text
submit_and_wait()
drain_used()
```

这样能保护：

- avail/used index；
- descriptor free list；
- token 到请求对象的表；
- in-flight 计数；
- MMIO interrupt acknowledge 与 used ring drain 顺序。

### 9.4 有界短轮询和协作让出

QEMU 中很多 4 KiB 请求在极短时间内完成，如果每次都立刻阻塞和唤醒，调度开销
可能高于设备延迟。

当前策略为：

```text
最多 64 次短轮询
  ├─ 已完成：直接返回
  ├─ need_resched：提前退出
  └─ 预算耗尽：无信号地 suspend/yield
                     ↓
                 恢复后继续检查
```

这参考 Linux blk polling 的 budget/need-resched 约束，但 CongCore 尚无上层
blk-mq waiter，因此预算耗尽后不是永久睡眠，而是让出 CPU 后恢复轮询。短轮询
和 IRQ 都调用 `drain_used()`；timer fallback 不是正常完成的主要路径。

队列真正满时使用 `queue_progress` generation 和 waitqueue：

1. 提交前读取 generation；
2. 尝试提交；
3. 若返回 `QueueFull`，等待 generation 改变；
4. 每个完成请求推进 generation 并唤醒一个提交者。

generation 的第一次读取发生在尝试提交之前，避免完成恰好落在“发现队列满”和
“开始等待”之间。

### 9.5 fallback polling 与诊断

正常运行依赖中断。timer fallback polling 被全局限制为最多每 10 ms 一次，
只用于早期启动、丢中断诊断和取得进展。

每个请求记录：

- 提交时间；
- 1 秒 stall warning；
- 30 秒 stuck warning；
- queue index；
- avail/used/last-used index；
- descriptor 使用量。

30 秒后不能安全地释放请求，只能报告。这是当前缺少 reset/recovery 的明确边界。

## 10. 架构相关的 IRQ 安全

### 10.1 RISC-V

RISC-V 内核在部分用户 trap 路径中保留用户 SATP。PLIC MMIO、VirtIO MMIO 和
DMA buffer 属于内核映射，不能假设硬中断发生时已经切到 kernel page table。

因此 PLIC 外部中断入口以及 VirtIO `handle_irq()`/fallback `poll()` 在触碰
设备前进入 `KernelPageTableGuard`。这对应 Linux 中设备中断始终运行于内核
地址空间的基本不变量。

相关文件：

- `os/src/arch/riscv64/irq.rs`
- `os/src/arch/riscv64/trap/handler.rs`
- `os/src/drivers/block/virtio_blk.rs`

### 10.2 LoongArch

LoongArch 使用 PCI VirtIO。驱动读取 PCI interrupt pin，并按 QEMU `virt`
host bridge 的 INTx swizzle 和 FDT interrupt-map 计算 IRQ：

```text
irq = 16 + (device + pin - 1) mod 4
```

相关文件：

- `os/src/arch/loongarch64/irq.rs`
- `os/src/drivers/block/virtio_blk.rs`
- `vendor/virtio-drivers-pci/src/transport/pci/bus.rs`

vendor 的旧同步路径已经对 LoongArch 强制 kick；新非阻塞路径沿用了该兼容行为。
Linux 本身没有按架构强制 kick 的特判。后续应按 Linux
`virtqueue_kick_prepare()` 修正 vendor 的 event-index 新旧 index 判断，再用
LoongArch QEMU 验证后移除该兼容项。

## 11. 关键并发不变量

实现和评审时使用以下不变量：

1. 不在持有 `BLOCK_CACHE_MANAGER` 时执行后端设备 I/O。
2. 不在持有 block-cache data lock 时等待设备写回。
3. 同一 cache key 最多有一个 loader。
4. loader 只能发布自己拥有的 `Loading(state)`。
5. 旧 generation 的写回不能清除新 generation 的 dirty 状态。
6. 同一磁盘 inode 的所有 Rust adapter 共用同一个 rw semaphore。
7. 多 inode write lock 按稳定 key 排序。
8. 硬中断和普通上下文共享的 spinlock 必须 irq-save。
9. request table 先取得请求所有权，再允许 IRQ 回收 token。
10. used ring 返回前，调用者 buffer 生命周期不能结束。
11. `on_cpu != OFF_CPU` 的任务不能直接重新入队。
12. wakeup pending 的发布和 idle 的 `on_cpu` 清除必须由同一 transition lock
    串行化。

### 14.1 总耗时

### 14.3 正确性观察

基线虽然最终返回码为 0，但三处 worker group 出现：

```text
Min xfer = 0
```

当前 24 个 worker group 的 `Min xfer` 全部非零，日志中也没有：

- VirtIO stall/error；
- panic；
- deadlock；
- IOZone 非零退出。

这不能代替完整文件系统一致性测试，但说明当前并发完成路径没有复现基线中的
worker 零进度现象。

### 14.4 如何解释性能分布

当前收益最明显的是 rewrite、缓存命中读取和 re-read：

- cache miss 不再阻塞全局 manager；
- 连续 extent 读可以合并为最多 128 KiB；
- 多个请求可以同时留在 VirtQueue；
- IRQ 或短轮询可以一次 drain 多个 used element；
- 不同 inode 的读操作不再竞争同一全局锁。

initial write 回退说明：

- 新块位图和 inode 位图仍需要共享 allocator metadata；
- 新文件创建包含目录项、inode 和 extent 更新；
- 当前 ext4 没有 journal batching 或 per-group allocator；
- 请求对象、`Arc` 和等待结构仍有分配成本；
- 预读对首次写没有帮助。

因此不能只根据总耗时改善宣布所有写路径都已优化完成。

## 17. 已知边界与后续工作

### 17.1 首次创建写

优先采集：

- ext4 allocator metadata lock 等待时间；
- block/inode bitmap 冷读次数；
- directory entry update 持锁时间；
- 每次 create 分配的请求对象和 `Arc` 数量；
- initial write 的 queue depth 和请求大小分布。

优化应参考 Linux ext4 per-group allocator 和 reservation 思路，不能为 IOZone
固定文件名或固定大小硬编码。

### 17.2 topology mutex 下沉到 filesystem

当前跨目录 rename 使用保守的全局 topology mutex。统一 VFS 建立稳定
`VfsFileSystem` 后，应把它变为 per-filesystem/superblock 锁，对应 Linux
`s_vfs_rename_mutex`。

### 17.3 修正 VirtQueue event-index

应实现 Linux 风格的：

```text
vring_need_event(event_idx, new_idx, old_idx)
```

随后删除 LoongArch 强制 kick，并在 LoongArch QEMU 上验证队列进展和中断完成。

### 17.4 从 block cache 走向统一 page cache

当前 single-flight 只协调 4 KiB ext4 block。后续统一 VFS/page cache 还需要：

- 以 inode + page index 为稳定 key；
- buffered read/write 与 shared mmap 共用页面；
- dirty page 和 writeback 状态；
- truncate/invalidate 与在途 I/O 协调；
- 后台 writeback 和回收；
- open-unlinked 生命周期。

### 17.5 完整块错误恢复

30 秒 stuck 诊断之后，未来应增加：

- 停止新提交；
- virtqueue/device reset；
- 取消或重新提交请求；
- 安全撤销 DMA mapping；
- 为每个请求返回可靠错误；
- 恢复队列服务。

在这些机制完成前，不能伪造 timeout success，也不能提前释放 DMA buffer。

## 19. 结论

本批次确认并修复了 P0 表格中“ext4 全局串行化 + VirtIO 同步等待”的主要结构
问题。修复后的关键变化不是简单地删除一把锁，而是同时建立：

```text
稳定 inode 锁身份
    + 多对象固定锁序
    + cache single-flight
    + 锁外 generation writeback
    + 有界 extent readahead
    + 多在途 VirtIO 请求
    + irq-safe 完成
    + 防丢唤醒的任务交接
```

这让不同 inode 的文件 I/O 开始具备真实并行性，并在聚焦 IOZone 中获得
`6.04%` 的中位总耗时改善和显著的 rewrite/read 吞吐提升。

同时，initial write 回退、全局 rename topology mutex、LoongArch 强制 kick
以及缺少完整 page cache/blk reset 都被保留为明确边界。下一阶段应继续以 Linux
可观察语义和并发协议为准，针对实测元数据瓶颈优化，而不是恢复全局锁或为单个
测试硬编码。
