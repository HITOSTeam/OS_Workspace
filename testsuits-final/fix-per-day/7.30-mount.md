# 7-30 挂载语义与对象化文件系统接入

## 问题概述

系统并未实现 统一的VFS 层 目前proc/ 等文件系统都是通过路径匹配在做，显然是不符合一切皆文件的语义的。为了防止后患无穷，还是早点做掉比较好。

## 如何发现

人工Review  ，检查发现本地 实现有如上问题。

## 怎么解决

核心关系改为：

```text
VfsFileSystem
  └─ root VfsNode
       ↑
VfsMount ── covered dentry / mount root
       ↑
VfsPath { mount, dentry }
       ↑
PathWalker 按分量 lookup，并在挂载点切换 mount
```

关于各个层次的意思，可以查看下面的详细介绍。

这样所有层次的文件系统，都可以通过impl 对应的trait 来完美接入。

# 可Mount 几种filesystem


| 文件系统 | 数据来源 | 能否创建普通文件 | 典型用途 |
|---|---|---:|---|
| ext4 | 磁盘块设备 | 可以 | 持久化文件 |
| tmpfs | 内存/交换空间 | 可以 | 临时文件 |
| procfs | 内核进程状态 | 通常不可以 | `/proc/<pid>`、系统信息 |
| sysfs | 内核对象和设备模型 | 通常不可以 | `/sys/devices` |
| devtmpfs | 内核设备注册信息 | 主要是设备节点 | `/dev/null`、`/dev/vda` |
| cgroupfs | 内核资源控制器 | 通常不可以 | CPU、内存等资源限制 |

### ext4

ext4 是真正的磁盘文件系统。

```text
open("/home/a.txt")
    ↓
查 ext4 inode
    ↓
读取磁盘数据块
```

它的数据重启后仍然存在。

### tmpfs

tmpfs 也是一个真正的、可读写的文件系统，但数据主要保存在内存中。

```sh
mount -t tmpfs tmpfs /tmp/memory
touch /tmp/memory/a.txt
echo hello > /tmp/memory/a.txt
```

它支持普通文件、目录、链接、权限等：

```text
tmpfs
├── a.txt
├── directory
└── symlink
```

卸载或重启以后数据通常消失。

因此 tmpfs 和 procfs 的关键区别是：

```text
tmpfs：存储用户写进去的普通文件
procfs：展示内核现场生成的信息
```

### procfs

procfs 展示进程和系统运行状态：

```text
/proc/uptime
/proc/meminfo
/proc/123/status
/proc/123/fd
```

例如读取：

```sh
cat /proc/uptime
```

不是从磁盘读取一个 `uptime` 文件，而是：

```text
read()
  ↓
procfs 向内核查询当前运行时间
  ↓
格式化成文本
  ↓
返回给用户
```

### sysfs

sysfs 展示内核对象和设备层次：

```text
/sys/devices
/sys/block
/sys/class
```

它关注的是：

```text
设备
驱动
总线
内核对象
设备属性
```

例如：

```text
/sys/block/vda/size
```

表示块设备 `vda` 的容量属性，不是磁盘中的普通文本文件。

### devtmpfs

devtmpfs 提供设备节点：

```text
/dev/null
/dev/zero
/dev/urandom
/dev/vda
```

打开这些路径以后，文件操作通常会转给设备驱动：

```text
open("/dev/vda")
    ↓
找到块设备节点
    ↓
read/write
    ↓
调用 VirtIO block 驱动
```

所以 `/dev/vda` 不是磁盘里的普通文件，它是访问设备的入口。

### cgroupfs

cgroupfs 把资源控制接口表现成目录和文件：

```text
/sys/fs/cgroup/cpu.max
/sys/fs/cgroup/memory.max
/sys/fs/cgroup/cgroup.procs
```

写入这些文件实际上是在修改内核资源控制状态：

```sh
echo 100M > memory.max
```

不是向普通文件保存 `"100M"`，而是让内核设置内存上限。


# VFS 中的一些 Utility struct

以test 为切入点 看看是如何起作用的

```text
1. Arc<TestFs>                 测试文件系统
2. Arc<VfsMountNamespace>     挂载命名空间
3. PathWalker                 路径解析器
4. VfsPath                    根路径对象
```

函数内部是：

```rust
fn root_fixture() -> (...) {
    let fs = TestFs::new(10);

    let namespace =
        VfsMountNamespace::new(Arc::clone(&fs) as Arc<dyn VfsFileSystem>);

    let root = namespace.root_path();

    let walker = PathWalker::new(Arc::clone(&namespace));

    (fs, namespace, walker, root)
}
```

### `Arc<TestFs>`

```rust
let fs = TestFs::new(10);
```

这是一个内存中的测试文件系统，ID 是 `10`。

初始结构只有根目录：

```text
TestFs id=10
└── /
```

测试可以通过它添加节点：

```rust
let a = fs.add(
    &fs.root,
    "a",
    2,
    VfsNodeKind::Directory,
);
```

添加后：

```text
/
└── a/
```

使用 `Arc` 是因为文件系统会同时被测试代码、mount 和 node 引用。

### `Arc<VfsMountNamespace>`

```rust
let namespace =
    VfsMountNamespace::new(
        Arc::clone(&fs) as Arc<dyn VfsFileSystem>
    );
```

它创建一个挂载命名空间，并把 `TestFs` 作为根文件系统：

```text
mount namespace
└── root mount
    └── TestFs id=10
```

后续可以在这个 namespace 中执行：

```rust
namespace.mount(...)
namespace.bind(...)
namespace.umount(...)
namespace.move_mount(...)
```

使用 `Arc` 是因为 `PathWalker` 和测试代码都需要引用同一个 namespace。

### `PathWalker`

```rust
let walker = PathWalker::new(Arc::clone(&namespace));
```

它是路径解析器，负责解析：

```text
/a/b/file
../file
symlink
mountpoint/child
```

它内部持有：

```text
mount namespace
positive dentry cache
```

解析时会逐级执行：

```text
root.lookup("a")
    → a.lookup("b")
    → b.lookup("file")
```

遇到挂载点时，还会查询 namespace 并进入新的 mount。

### `VfsPath`

```rust
let root = namespace.root_path();
```

这是 namespace 的根路径对象。

它不是字符串 `"/"`，而是两个对象的组合：

```rust
VfsPath {
    mount: 根挂载对象,
    dentry: 根目录项对象,
}
```

也就是：

```text
VfsPath = 在哪个 mount 中 + 指向哪个 dentry
```

这比字符串路径更准确。即使两个 mount 中都有 `/file`，它们的 `VfsPath` 也不同。

### 四者的关系

```text
TestFs
  提供根 node 和 lookup 操作
       ↓
VfsMountNamespace
  把 TestFs 挂载为根文件系统
       ↓
VfsPath
  指向 namespace 中的根 mount + 根 dentry
       ↓
PathWalker
  从 VfsPath 出发，在 namespace 中解析路径
```

测试通常这样接收：

```rust
let (fs, namespace, walker, root) = root_fixture();
```

然后：

```rust
// 在测试文件系统中创建 /a
fs.add(&fs.root, "a", 2, VfsNodeKind::Directory);

// 从 root 开始解析 /a
let result = walker.walk(
    &root,
    &root,
    "/a",
    LookupFlags::default(),
    VfsCredentials::default(),
);
```

如果某个测试不需要 namespace，可以写：

```rust
let (fs, _, walker, root) = root_fixture();
```

这里的 `_` 表示忽略第二个返回值。

# 如何接入一个文件系统 以 ext4为例

核心是两个trait
filesystem + Node 的trait

```rust
impl VfsFileSystem for Ext4Vfs {
    fn filesystem_id(&self) -> u64 {
        self.filesystem_id
    }

    fn filesystem_type(&self) -> &'static str {
        "ext4"
    }

    fn root_node(&self) -> Arc<dyn VfsNode> {
        Arc::new(Ext4VfsNode::new(self.filesystem_id, Arc::clone(&self.root)))
    }

    fn statfs(&self) -> VfsResult<VfsStatFs> {
        Ok(VfsStatFs {
            magic: EXT4_SUPER_MAGIC,
            block_size: self.root.block_size() as u64,
            name_len: 255,
            ..VfsStatFs::default()
        })
    }

    fn sync(&self) -> VfsResult<()> {
        ext4_fs::sync_all();
        Ok(())
    }
}
```
可以看到底层的细节由ext4_fs包实现，我们这里只是做一个包装而已
inode 的细节较多 我们这里忽略

# tmpfs

tmpfs 是一个在内存中的文件系统

临时文件系统

这一点可以从 fsinode 见得

```rust

enum TmpFsData {
    /// 目录项名称到节点对象的有序映射；多个名称可以指向同一个硬链接节点。
    Directory(BTreeMap<String, Arc<TmpFsNode>>),
    /// 稀疏普通文件：key 为页号，只为实际写入过的 4 KiB 页分配内存。
    Regular(BTreeMap<usize, Box<[u8; PAGE_SIZE]>>),
    /// 符号链接保存未经解析的目标字符串。
    Symlink(String),
    /// FIFO、字符/块设备和 socket 等当前只保存元数据的特殊节点。
    Special,
}

```

文件系统依然是那套inner 分离写 与 只读部分：

```rust


/// 由节点局部 `RwLock` 保护的可变状态。
struct TmpFsNodeInner {
    /// Linux 可观察的节点类型、权限、owner、链接数、大小和时间戳。
    metadata: VfsMetadata,
    /// 与节点类型对应的目录、稀疏页、symlink 或特殊节点数据。
    data: TmpFsData,
    /// 节点的扩展属性名称和值。
    xattrs: BTreeMap<String, Vec<u8>>,
}

/// TmpFs 中具有稳定 inode 身份的文件系统节点。
///
/// 目录项、dentry 和打开文件均通过 `Arc` 持有节点，因此 unlink 只会移除
/// 名称；节点会一直存活到最后一个引用被释放。
pub struct TmpFsNode {
    /// 所属 TmpFs 的弱引用，避免文件系统与节点形成强引用环。
    fs: Weak<TmpFs>,
    /// 在所属 TmpFs 实例内稳定且唯一的 inode 编号。
    inode: u64,
    /// 节点局部可变状态；普通 lookup/read 可以并发获取读锁。
    inner: RwLock<TmpFsNodeInner>,
}
```
