# 7-30 LoongArch 多核支持与批量精确 TLB Shootdown

## 问题概述

QEMU 创建多个虚拟处理器并不等于内核已经支持对称多处理（Symmetric
Multiprocessing，SMP）。LoongArch 还需要发现处理器拓扑、唤醒次级处理器、为每个
处理器准备独立启动栈和本地异常状态，并在页表变化时让所有正在使用该地址空间的核心
失效转换检测缓冲区（Translation Lookaside Buffer，TLB）中的旧记录。旧的保守方案
会为每个页表项修改清空整个地址空间，正确但代价过高。

## 如何发现

源码审查显示启动代码只完成启动处理器路径，页表修改也缺少 LoongArch 跨核完成协议。
验证使用相同内核分别以 1、2、4、12 个虚拟处理器启动，并检查固件设备树发现掩码和
最终在线掩码；原文没有保留这些早期启动矩阵的独立日志目录，因此只记录结果，不补造
日志路径。可复核命令与代码检索为：

```sh
ARCH=loongarch64 SMP=12 MEM=8G IMAGE_MODE=snapshot ./run.sh shell
rg -n 'HartTopology|present_mask|online_hart_mask|IOCSR_MBUF_SEND|SMP_BOOT_CPU' \
  os/src/arch/loongarch64 os/src/mm/dtb.rs os/src/main.rs
rg -n 'PageTableUpdateBatch|record_page|record_range|drop_asid' os/src/mm
```

运行中以 online mask 验证次级核心只有在内存管理单元、异常入口、定时器和处理器间
中断全部初始化后才发布在线状态；`tlb_shootdown_smp_smoke` 则让两个共享地址空间的
线程固定在不同核心，反复修改 4 KiB、64 KiB 和 4 MiB 映射权限。打开 `DEBUG_PERF`
后还可从 `/proc/perf` 读取 page/range/ASID 失效批次和远端中断数。

## 怎么解决

启动路径先从固件设备树（Flattened Device Tree，FDT）的 `/cpus` 节点建立物理
hart 掩码，再通过输入输出控制与状态寄存器（Input/Output Control and Status
Register，IOCSR）mailbox 写入 `_start` 地址并发送启动中断。每个 hart 在汇编入口按
物理编号选择独立 64 KiB 栈，等待启动核发布全局初始化完成，随后初始化本地页表、
异常、定时器和中断，最后设置 online bit。

页表更新由事务对象收集范围：

```text
修改若干 PTE
  -> record_page()/record_range()
  -> 相邻 8 KiB TLB pair 合并
  -> 小范围逐 pair invtlb；大范围 drop ASID
  -> 每个目标 hart 只发送一次 IPI
  -> 等待 completion sequence
  -> 所有 ack 到达后才释放旧 frame
```

地址空间标识符（Address Space Identifier，ASID）按 hart 保存 generation；active-hart
掩码记录哪些核心可能缓存该地址空间。发送方先发布页表项，再写目标 mailbox 并发送
处理器间中断（Inter-Processor Interrupt，IPI）；接收方执行本地 `invtlb` 后更新完成
序号。等待期间也服务自己的入站失效，避免两个核心互相等待。

Linux LoongArch 的 `arch/loongarch/kernel/smp.c`、`arch/loongarch/mm/tlb.c` 和
`mm_cpumask()` 提供相同边界。CongCore 用固定掩码和 mailbox 请求矩阵代替 Linux 的
通用 `smp_call_function_many()`，但保留“只通知相关核心、按范围失效、确认完成后再
复用物理页”的关键语义。

本批次把 LoongArch 从“QEMU 创建了多个 vCPU，但内核只使用启动核”推进到一条
完整的 SMP 路径：

```text
FDT 发现 CPU
    -> IOCSR mailbox 唤醒二级核
    -> 每 hart 初始化 MMU/trap/timer/IPI
    -> 发布 online mask
    -> 每 hart 进入调度器
    -> reschedule IPI 唤醒和抢占
    -> ASID + 跨核 TLB shootdown 保证共享页表一致性
```

“二级核打印 online”不是完成标准。多核真正可用还要求启动协议、初始化顺序、
调度、跨核中断和内存管理形成闭环。尤其是页表修改：一个 hart 更新 PTE，并不
代表其他 hart 已经看见新映射；其他 hart 的 TLB 中可能继续保留旧权限、旧物理
页或已经解除的映射。

最保守的 TLB 处理方法是每次修改 PTE 都通知所有 CPU，并刷新整个用户 TLB。
它容易保证正确性，却把一个 4 KiB 页的 COW fault、一次小范围 `mprotect`，
甚至同一 syscall 内连续修改的多个 PTE，都变成昂贵的同步跨核操作。

本批次参考 Linux LoongArch 的 ASID 与 TLB range flush 策略，把原来的粗粒度
路径改造成：

> 单页精确失效，小范围逐页对失效，大范围才 drop ASID；同一页表更新事务中的
> 多个修改合并后，每个远端 hart 最多发送一次 IPI。

这项改动首先保证多核页表一致性，同时缩小 TLB 失效范围、减少 IPI 次数和无效
TLB refill。实现位于 LoongArch SMP 工作树，尚未形成正式提交。

## 1. 先明确 LoongArch 的启动模型

RISC-V 可以通过 SBI HSM `hart_start` 启动其他 hart，也可以调用 SBI remote
fence。LoongArch QEMU `virt` 机器不是这套接口，不能直接复用 RISC-V 路径。

QEMU direct boot 时，二级 vCPU 停在 boot ROM。启动核需要：

1. 把二级核入口地址写入目标 CPU 的 IOCSR mailbox 0；
2. 入口地址为 64 位，因此分别发送高、低 32 位；
3. 执行内存屏障，确保 mailbox 内容先于启动通知可见；
4. 通过 `IOCSR_IPI_SEND` 发送 bit 0 `SMP_BOOT_CPU`；
5. boot ROM 取出入口并跳转到内核 `_start`。

Linux LoongArch 也使用 mailbox 0 和 boot IPI 完成这段协议。当前
`arch::hart_start()` 按相同布局构造 `IOCSR_MBUF_SEND`：

```text
boot hart
   │
   ├─ mailbox[secondary] <- high32(_start)
   ├─ mailbox[secondary] <- low32(_start)
   ├─ dbar 0
   └─ IPI action bit 0
                         │
secondary boot ROM      ▼
                    jump _start
```

实现集中在：

- `os/src/arch/loongarch64/mod.rs`
- `os/src/arch/loongarch64/csr_defs.rs`
- `os/src/main.rs`

## 2. 从 FDT 发现真实 CPU 拓扑

旧代码按 `0..MAX_HARTS` 假定所有 CPU 都存在。这在固定 QEMU 参数下可能工作，
但只要 `-smp` 数量变化，就会向不存在的 hart 发送启动请求，或者让数组容量与
硬件数量不一致。

启动核现在解析 FDT `/cpus` 节点，构造基于物理 hart ID 的
`present_mask`：

```text
HartTopology
 ├─ present_mask   FDT 中存在且内核支持的物理 hart
 ├─ discovered     FDT 中发现的 CPU 总数
 └─ ignored        超出 MAX_HARTS 或位图宽度的 CPU 数
```

这里刻意保留物理 ID，而不是把它们重新压缩为逻辑编号。mailbox、IPI 目标和
`CSR.CPUID` 都使用物理 ID，提前重编号会让“调度器认为的 CPU 1”和“硬件收到
IPI 的 CPU 1”产生歧义。

异常情况下采用保守回退：

- DTB 地址为空或解析失败时，只启用 boot hart；
- 无有效 CPU 节点时，只启用 boot hart；
- boot hart 始终被加入 `present_mask`；
- 超出容量的 CPU 被计数并忽略，不允许越界访问 per-hart 数组。

决赛 LoongArch QEMU 配置最多使用 12 个 vCPU，因此 `MAX_HARTS` 提升为 12。
这个常量同时约束 early stack、processor、runqueue、timer、IPI request、
ASID context 等结构，避免不同子系统各自保留 4、8、12 等不一致上限。

拓扑发现位于 `os/src/mm/dtb.rs`。

## 3. 每个 hart 必须有独立的 early stack

所有 CPU 都从同一个 `_start` 进入，但不能共用启动栈。入口先读取
`CSR.CPUID`，再按物理 hart ID 选择 64 KiB 的独立区域：

```text
sp(hart) = boot_stack_top - hart_id * 64 KiB
```

汇编中的栈总大小不再写死为 4 核，而是由 Rust `global_asm!` 把
`config::MAX_HARTS` 传入：

```text
.space 64 KiB * MAX_HARTS
```

在计算栈地址前还会检查 `hart_id < MAX_HARTS`。不支持的 hart 留在
`idle 0` 循环，不能用越界栈进入 Rust。这个检查必须发生在任何栈访问之前，
否则一个意外启动的高编号 CPU 可以直接覆盖 BSS 或其他 hart 的栈。

对应文件为 `os/src/entry_loongarch.S`。

## 4. 启动屏障与每 hart 初始化

全局对象只能由 boot hart 初始化一次，而大量 CSR 又必须在每个 hart 上分别
设置。实现把启动过程拆成三个阶段：

```text
BOOT_HART_INITED
    选出唯一 boot hart
          │
          ▼
BOOT_BSS_CLEARED
    boot hart 已清理 BSS
          │
          ▼
BOOT_GLOBAL_INIT_DONE
    堆、页表、设备和全局调度状态可用
```

boot hart 执行：

1. 清理 BSS；
2. 解析 FDT，发布 `present_mask`；
3. 初始化物理内存、堆和共享内核页表；
4. 初始化本地 MMU、trap、timer 和 IPI；
5. 用 release store 发布 `BOOT_GLOBAL_INIT_DONE`；
6. 按 `present_mask` 唤醒二级 hart；
7. 等待期望的 online mask，超时打印缺失位图；
8. 创建 init task 并进入调度器。

二级 hart 用 acquire load 等待屏障，随后执行自己的本地初始化：

- 安装共享内核页表根；
- 配置 CRMD paging 状态；
- 设置 TLB refill 入口；
- 配置 STLB 页大小和 page-walk CSR；
- 初始化本地 ASID/TLB 容量信息；
- 安装 trap 入口；
- 启用本地 timer 与 IPI；
- 设置下一次时钟事件；
- 最后才设置 online bit 并进入自己的 scheduler loop。

这里“最后才 online”很重要。调度器只能把任务放到已经具备页表、异常入口、
timer 和 IPI 能力的 hart，否则用户态可能被调度到一个尚未完成初始化的 CPU。

启动核等待 secondary 的最长时间为 5 秒。超时不会静默卡死，而会输出：

```text
expected mask
online mask
missing mask
```

这让 mailbox 失败、入口失败和某个 hart 初始化卡住可以被区分。

## 5. 每 hart 调度器、runqueue 与 idle

二级核启动后不能进入一个空循环；每个 hart 都需要独立的调度上下文。调度层
已经按 `MAX_HARTS` 维护：

- `PROCESSORS[hart]`
- per-hart ready queue
- `NEED_RESCHED[hart]`
- per-hart timer/clockevent 状态
- 当前运行任务与 `on_cpu` 归属

boot hart 只初始化一次 `INITPROC`，secondary 直接调用
`task_start_secondary()` 进入自己的 idle/scheduler loop，避免多个 CPU 重复
创建 init 进程。

任务入队时只在 `online_hart_mask` 与 affinity 的交集中选择目标。新任务会在
允许的在线 hart 中分散；wakeup 尽量保留上次运行 CPU 的局部性，必要时再迁移。
如果任务被放入远端空队列，或它应该抢占远端当前任务，发送 reschedule IPI。

远端处理后设置调度条件，真正的抢占发生在安全点：

- timer tick；
- syscall 返回；
- trap 返回用户态前的 `NEED_RESCHED` 检查；
- 当前任务主动阻塞或让出。

空闲 hart 原来使用 `spin_loop()` 忙等，现在打开中断后执行 LoongArch
`idle 0`。timer 或 IPI 会唤醒它，再回到 scheduler 顶部检查 ready queue。
这既降低无任务时的 CPU 占用，也让“远端入队 + IPI kick”形成完整唤醒路径。

## 6. IPI action 与用户可见的 SMP 语义

IOCSR IPI action 位与 Linux LoongArch 的基本分类对齐：

| 位 | 名称 | 当前用途 |
| ---: | --- | --- |
| 0 | `SMP_BOOT_CPU` | 从 QEMU boot ROM 唤醒二级核 |
| 1 | `SMP_RESCHEDULE` | 唤醒 idle hart 或请求远端重新调度 |
| 2 | call-function 类动作 | 执行待处理的 TLB shootdown |

每个 hart 都会启用 ECFG 的 IPI local-enable 位和 IOCSR IPI enable。handler
先清除硬件 pending action，再处理软件请求，避免旧 pending 位导致重复陷入。
IPI 在用户态和允许嵌套中断的内核路径中都能被处理。

用户态看到的 CPU 语义也与真实 online mask 连接：

- `sched_getaffinity` 只返回在线且允许的 CPU；
- `sched_setaffinity` 更新任务允许集合并触发必要迁移/重调度；
- `getcpu` 返回当前物理 hart；
- `/proc` 中的 CPU 与中断信息按 online hart 输出；
- `getcpu01` 在 12 核运行中实际观察到 CPU 11，而不是始终返回 CPU 0。

到这里，多核已经具备“发现、启动、调度、唤醒、用户可见”的基本能力。下一部分
解决多 hart 共享地址空间后最关键的内存一致性问题。

## 7. 原问题为什么会影响多核性能

一次页表更新需要完成两件不同的事情：

1. 把新 PTE 写入内存；
2. 让所有可能缓存旧翻译的 hart 丢弃对应 TLB 项。

如果只做第一步，同一地址空间的另一个线程仍可能：

- 在 `mprotect(PROT_READ)` 后继续使用旧的可写翻译；
- 在 COW 替换物理页后继续访问旧页；
- 在 `munmap` 后继续访问已经释放、甚至已经被复用的物理页；
- 因为保留旧的只读项而产生重复写异常。

旧路径还有一个 LoongArch 指令语义问题：它把地址传给了 `invtlb 0x4`。但
操作码 `0x4` 只按 ASID 匹配，地址操作数不参与匹配。因此代码看起来像“刷新
一页”，实际上会丢弃该 ASID 的全部非全局项。

于是一次修改多页的 syscall 可能退化为：

```text
修改 PTE 0 -> drop 整个 ASID -> IPI -> 等待 ack
修改 PTE 1 -> drop 整个 ASID -> IPI -> 等待 ack
修改 PTE 2 -> drop 整个 ASID -> IPI -> 等待 ack
...
```

性能损失不只来自 `invtlb` 指令本身，还包括：

- 每次同步 IPI 的发送、陷入和返回；
- 发起 hart 等待所有目标 hart 确认；
- 目标 hart 被迫中断当前工作；
- 整个 ASID 的热 TLB 项被清空，后续访问重新 page walk；
- 多个 hart 同时修改同一 mm 时产生同步放大。

对单核或短测试，这种代价不一定明显；对共享地址空间、多线程 allocator、
频繁 COW、`mprotect`/`munmap` 和并行编译场景，它会进入热路径。

## 8. LoongArch 的精确失效粒度

LoongArch 一个普通 TLB 项包含偶数页和奇数页两个 `TLBELO`，在当前 4 KiB
页配置下，一个 TLB 项覆盖相邻的 8 KiB 页对。因此“单页精确失效”的硬件实际
粒度是包含该页的 8 KiB TLB 页对，而不是任意单个 4 KiB 半项。

本实现使用以下操作：

| 操作码 | 匹配范围 | 使用场景 |
| --- | --- | --- |
| `0x5` | 非全局项，ASID + 虚拟地址 | 单页和小范围用户映射 |
| `0x4` | 非全局项，ASID | 大范围用户映射，drop ASID |
| `0x3` | 当前 hart 的全部非全局项 | 本地 ASID generation 回绕 |
| `0x1` | 当前 hart 的全部 TLB 项 | 共享内核映射发生变化 |
| `0x6` | 全局项，或匹配 ASID + 地址 | 低层页表 API 的当前地址失效 |

记录区间时，起止地址都按 8 KiB 页对扩展：

```text
pair_start = align_down(start, 8 KiB)
pair_end   = align_up(end, 8 KiB)
pair_count = (pair_end - pair_start) / 8 KiB
```

所以修改一个 4 KiB PTE 时只执行一次地址精确的 `invtlb 0x5`，不会再清空
该进程的其他热翻译。

对应代码主要位于：

- `os/src/arch/loongarch64/csr_defs.rs`
- `os/src/arch/loongarch64/mm/asid.rs`
- `os/src/arch/loongarch64/mm/page_table.rs`

## 9. 单页、range 与 drop ASID 的分界

逐页对执行 `invtlb` 并不总是最优。范围足够大时，一次按 ASID 失效比执行数百
次地址失效更便宜；过大的失效消息也不适合放进固定大小的无锁 IPI payload。

每个 hart 初始化时从 `PRCFG3` 探测 MTLB/STLB 组织，计算精确失效的容量截止
值。策略与 Linux LoongArch 保持一致：

- 只有 MTLB 时，精确失效上限取总容量的 `1/2`；
- 同时存在 STLB 时，上限取总容量的 `1/8`；
- 系统使用各在线 hart 探测值中的最小值，保守覆盖可能不同的 CPU 配置；
- 合并后超过 8 个离散区间，或页对总数超过截止值时，退化为 drop ASID。

最终决策大致是：

```text
                     PTE 修改
                        │
                        ▼
              对齐到 8 KiB TLB 页对
                        │
                        ▼
               合并重叠和相邻区间
                        │
           ┌────────────┴────────────┐
           │ ranges <= 8 且           │ 否
           │ pairs <= TLB cutoff      ├─────────┐
           └────────────┬────────────┘         │
                        │ 是                    ▼
                        ▼                 retire context
              ASID + address 精确失效       + invtlb 0x4
```

这不是固定用页数猜测，而是根据 CPU 实际 TLB 容量选择成本较低的路径。典型
结果是：

- 4 KiB COW/fault：一次 8 KiB 页对失效；
- 64 KiB `mprotect`：一个合并 range，循环失效少量页对；
- 4 MiB `mprotect`：超过阈值，直接 drop ASID。

## 10. 用页表更新事务合并多个修改

只优化 `invtlb` 操作码还不够。如果 `munmap` 每删一个 PTE 就立即提交一次
shootdown，IPI 次数仍然与页数成正比。

为此，LoongArch 的 `MemorySet` 增加了 `PageTableUpdateBatch`。它以一次内存
管理操作为事务边界，记录：

- 被修改的单页或区间；
- 合并后的最多 8 个 range；
- 修改 PTE 的总次数；
- shootdown 完成前不能释放的旧 `FrameTracker`；
- 是否包含必须全 TLB 失效的共享内核映射。

相邻或重叠区间在记录时立即合并。例如同一 syscall 依次修改：

```text
[0x1000, 0x2000)
[0x2000, 0x3000)
[0x5000, 0x6000)
```

按 TLB 页对对齐后可合并为更少的区间，最后只提交一次 shootdown。事务的
`commit` 和 `Drop` 都会完成失效，避免错误返回路径漏掉提交。

当前已经接入的路径包括：

- `mprotect`
- `munmap`
- `madvise`
- `mremap`
- fork 时建立 COW
- COW 写异常
- lazy fault
- shared mapping 更新
- 内核栈移除

因此“一个 syscall 内多次修改页表”不再等于“发送多次 IPI”。远端 IPI 数量
主要由真正运行该 mm 的 hart 数量决定，而不是被修改的 PTE 数量决定。

## 11. 每 hart ASID 与 active hart 跟踪

硬件 TLB 是 per-hart 资源，因此同一个 mm 不必在所有 hart 上使用同一个
ASID。本实现给每个地址空间保存：

```text
AsidContext
 ├─ hart_contexts[hart] = generation | local ASID
 ├─ active_harts
 └─ invalidation_sequence
```

每个 hart 独立维护 `next_user_asid` 和 `asid_generation`。ASID 0 保留给内核，
可用 ASID 位数从 `CSR.ASID.ASIDBits` 探测。

`active_harts` 表示当前正在用户态执行这个 mm，或处于最终返回用户态窗口的
hart。它让失效路径可以区别处理：

- active hart 可能正在使用旧翻译，必须发送 IPI 并等待确认；
- inactive hart 已经使用内核 ASID 0，不必立即打断，只需退休该 mm 在该 hart
  上的旧 context；
- 该 mm 下次调度到此 hart 时分配新 ASID，旧 TLB 项不会再次被选中；
- 当本地 ASID 空间回绕时，generation 增加，并清空当前 hart 的非全局项，
  防止旧 ASID 被重新使用。

这比无条件向所有 online hart 广播更接近 Linux 的 lazy TLB 思路。CPU 数量
增加时，IPI fan-out 由“全部 CPU”缩小为“确实可能使用旧翻译的 CPU”。

## 12. 失效序号关闭用户态返回竞态

只读取一次 `active_harts` 不足以保证正确性。考虑以下竞态：

```text
hart 0                              hart 1
开始修改页表
读取 active_harts，未看到 hart 1
                                    正准备返回同一个 mm 的用户态
修改 PTE
不向 hart 1 发 IPI
                                    带着旧 ASID 返回用户态
```

实现使用奇偶 `invalidation_sequence` 形成 mm-local 轻量 seqlock：

1. invalidator 把 sequence 从偶数改为奇数；
2. 奇数期间，新的用户态返回不能提交 active bit；
3. 完成 PTE 修改、IPI 和 ack；
4. sequence 恢复为偶数；
5. 与失效并发的返回路径撤销 active bit，重新获取有效 context 后再返回。

这样 `active_harts` 的快照与“谁可以进入用户态使用旧 ASID”形成闭环。该机制
只覆盖一个 mm，不需要全局页表失效锁。

## 13. 无锁 IPI 请求矩阵与一次性通知

TLB shootdown 使用固定的请求矩阵：

```text
requests[target_hart][source_hart]
```

每个 source 独占目标上的一个槽位，槽位包含：

```text
request sequence
ack sequence
kind
target ASID
range count
range[8]
```

发送流程如下：

1. 发起 hart 完成全部 PTE store；
2. `dbar 0` 保证页表写在请求发布前全局可见；
3. 填充每个目标 hart 的 payload；
4. 用 release store 发布新的 request sequence；
5. 每个远端目标只发送一次 bit 2 call-function 类 IPI；
6. 本 hart 直接执行相同的本地失效；
7. 等待所有目标把 ack 更新到本次 sequence。

目标 hart 用 acquire load 读取请求，扫描来自不同 source 的槽位。如果同一时刻
存在多类请求：

- full TLB 请求覆盖其他所有请求；
- user-all 请求覆盖 ASID/range 请求；
- 否则按各 source 的 ASID 和 range 执行精确失效。

独立 source 槽位避免两个 hart 同时发请求时互相覆盖，也不需要一把全局
shootdown 锁。固定数组还避免在 IPI handler 中动态分配内存。

## 14. 两个容易遗漏的并发正确性问题

### 14.1 必须等待 ack 后才能释放旧物理页

`munmap` 或 COW 替换 PTE 后，旧 `FrameTracker` 不能马上 drop。否则可能发生：

```text
hart 0 更新 PTE 并释放旧页
        │
        ├─ 物理页被 allocator 分给其他对象
        │
hart 1 仍通过陈旧 TLB 写入旧物理页
        ▼
新对象内容被破坏
```

`PageTableUpdateBatch` 把旧 frame 保存在 `deferred_frames` 中。只有所有目标
hart 确认完成失效后，才允许这些 frame 进入 allocator，形成：

```text
PTE store -> publish request -> remote invtlb -> ack -> release old frame
```

因此同步等待不仅是性能代价，也是物理页生命周期的正确性边界。

### 14.2 等待 shootdown 时也要服务入站请求

如果 hart 0 和 hart 1 同时修改同一个或不同 mm，可能互相发送 shootdown：

```text
hart 0 等待 hart 1 ack
hart 1 等待 hart 0 ack
```

如果两边只自旋等待，就会形成环路。发送端在等待期间会主动调用
`service_pending_tlb_shootdowns()`，先完成别人发给自己的请求，再继续检查
自己的 ack。

另一个锁序问题发生在共享 `MemorySet` 的 `CLONE_VM` 线程之间：发送者可能
持有 mm 锁等待目标 ack，而目标从用户态进入异常后又先尝试获取同一把 mm 锁。
LoongArch trampoline 此时已经切换到内核页表和 ASID 0，因此 trap handler
现在先处理无锁 TLB 请求并确认，再清除 active bit、获取其他内核锁。这避免了：

```text
sender: holds MemorySet lock -> waits for ack
target: waits for MemorySet lock -> cannot ack
```

普通 syscall 和较长 timer 工作期间也允许 IPI 被及时处理；嵌套 timer 工作则
继续延后，避免重新进入复杂调度路径。

## 15. 性能观测

打开 `DEBUG_PERF` 后，`/proc/perf` 增加以下指标：

- `tlb_page_batches`
- `tlb_range_batches`
- `tlb_asid_drops`
- `tlb_batched_edits`
- `tlb_merged_ranges`
- `tlb_exact_pairs`
- `tlb_remote_ipis`
- `tlb_shootdown_wait_cycles`
- `tlb_asid_wraps`

这些指标可以回答比“测试是否通过”更重要的问题：

- PTE 修改有多少真正命中单页或 range 路径；
- 每个 batch 平均合并了多少次修改；
- 一个事务平均发送多少远端 IPI；
- 同步等待占用了多少周期；
- ASID 容量是否足够，是否频繁发生 generation 回绕。

目前已经验证结构性优化和并发正确性，但还没有记录 BuildStorm 修改前后的严格
同环境耗时，因此不声明未经测量的加速百分比。

## 16. 启动矩阵与专用多核回归

同一个 LoongArch release 内核使用不同的 QEMU `-smp` 参数启动，FDT mask 与
online mask 一致：

| `-smp` | 期望 mask | online mask | 结果 |
| ---: | ---: | ---: | --- |
| 1 | `0x1` | `0x1` | 通过 |
| 2 | `0x3` | `0x3` | 通过 |
| 4 | `0xf` | `0xf` | 通过 |
| 12 | `0xfff` | `0xfff` | 通过 |

这组测试不只检查启动日志：只有 secondary 完成本地 MMU、trap、IPI、timer
初始化并调用 `mark_hart_online()`，对应位才会出现在 online mask 中。

新增 `tlb_shootdown_smp_smoke`，测试两个共享同一 mm 的线程：

- 父线程固定到 CPU 0；
- 子线程固定到 CPU 1；
- 预先物化 4 MiB 匿名映射，确保测试操作真实修改已存在的 PTE；
- 子线程依次对 4 KiB、64 KiB 和 4 MiB 执行只读/可写
  `mprotect` 往返；
- 父线程持续读取热地址，迫使远端 TLB 一致性路径真正参与；
- 最后检查线程退出状态以及映射首尾页内容。

三种范围分别覆盖：

| 范围 | 预期路径 |
| ---: | --- |
| 4 KiB | 单个 8 KiB TLB 页对精确失效 |
| 64 KiB | 合并后的小范围失效 |
| 4 MiB | 超过容量截止值，drop ASID |

完成的验证包括：

- LoongArch64 内核静态检查；
- RISC-V 内核静态检查，确认条件编译路径未退化；
- LoongArch release 内核和用户镜像构建；
- QEMU `-smp 1/2/4/12` 启动并形成完整 online mask；
- 4 核专用 TLB smoke 通过；
- 12 核专用 TLB smoke 连续三次通过；
- 12 核 `getcpu01` 实际观察到 CPU 11；
- `mprotect01/03`、`munmap03`、`mremap01-05` 聚焦回归通过；
- 两个 Cargo workspace 的格式检查与 `git diff --check`。

## 17. 与 Linux 的关系和剩余差距

本实现参考了 Linux LoongArch 的以下机制：

- IOCSR mailbox + boot IPI 的 secondary 启动协议；
- reschedule/call-function 类 IPI action；
- per-CPU ASID context；
- 根据 `PRCFG3` TLB 容量选择 range flush 或 ASID flush；
- 通过 call-function 类 IPI 执行远端失效；
- 地址精确的 `invtlb` 操作码。

参考源码：

- [Linux LoongArch SMP 启动与 IPI](https://github.com/torvalds/linux/blob/master/arch/loongarch/kernel/smp.c)
- [QEMU LoongArch direct boot](https://github.com/qemu/qemu/blob/master/hw/loongarch/boot.c)
- [Linux LoongArch TLB 操作定义](https://github.com/torvalds/linux/blob/master/arch/loongarch/include/asm/tlb.h)
- [Linux LoongArch range flush](https://github.com/torvalds/linux/blob/master/arch/loongarch/mm/tlb.c)
- [Linux LoongArch CPU/TLB 能力探测](https://github.com/torvalds/linux/blob/master/arch/loongarch/kernel/cpu-probe.c)

当前实现仍不是 Linux 完整 SMP/MM 子系统：

- CPU 拓扑在启动时静态确定，尚未实现 CPU hotplug/offline；
- 调度器没有 Linux 完整的 sched-domain、NUMA 和周期负载均衡模型；
- IPI bit 2 目前是专用 TLB 请求矩阵，还不是通用
  `smp_call_function_many()` 队列；
- range payload 固定为 8 段，复杂 VMA 编辑会保守退化为 ASID 失效；
- shootdown 仍需同步等待，尚未实现更完整的 lazy-mm、RCU page-table
  reclamation 或异步释放策略；
- 尚缺 BuildStorm 前后对照数据和真实 Loongson 硬件验证；
- LoongArch LSX 上下文仍未实现，相关用户程序端到端门禁需要单独处理。

这些限制不影响本批次的核心语义：小修改不再无条件清空整个地址空间，多次 PTE
编辑不会重复发送 IPI，而旧物理页只有在所有相关 hart 确认失效后才会被复用。
