# 7-30 LoongArch 多核支持与批量精确 TLB Shootdown

## 问题概述

LoongArch 内核只使用启动核，其余 11 个 vCPU 停在 boot ROM。同时 TLB 刷新使用
错误的 `invtlb` 操作码——看起来像"刷一页"，实际清掉了整个 ASID 的所有条目。
一次修改多页的操作退化为 N 次全 ASID 刷新 + N 次 IPI。

本批参考 Linux LoongArch 的 SMP 启动和 TLB shootdown 机制，实现了从 FDT 发现
CPU、IOCSR mailbox 唤醒从核、per-hart ASID 分配，到按范围精确失效和跨核同步的
完整路径。

## 背景知识

这一节给只上过操作系统课的读者铺路。

**TLB 是页表的高速缓存**。CPU 每次访问虚拟地址都要查页表把虚拟页号翻译成物理
页号。多级页表在内存里，查一次要好几次内存访问。TLB 把最近用过的翻译结果存在
硬件里，命中就直接用，不命中再去查页表（这叫 TLB miss）。

**LoongArch 有两块 TLB，查找时并行查**：

```text
              ┌─────────────────────────────────────┐
   虚拟地址 ──┤                                     │
              │  ┌───────────┐   ┌───────────────┐  │
              ├─>│   MTLB    │   │     STLB      │<─┤
              │  │ 全相联    │   │ 组相联        │  │
              │  │ 每项自带  │   │ 固定页大小    │  │
              │  │ 页大小    │   │ (4 KiB)       │  │
              │  │ (~48 项)  │   │ (数百~千项)   │  │
              │  └─────┬─────┘   └───────┬───────┘  │
              │        │  命中任一即可   │          │
              │        └────────┬────────┘          │
              └─────────────────┼───────────────────┘
                                ▼
                          物理页号 + 属性
```

- **STLB**（Single Page Size TLB）：全表只能装一种固定页大小（本项目设为 4 KiB），
  组相联结构（就像 CPU cache 分组），容量大。类比：专用车道，只跑一种车型但通道多。
- **MTLB**（Multiple Page Size TLB）：全相联，每项自带页大小字段，可以混装
  4 KiB、2 MiB 等。类比：VIP 车位，什么车都能停但只有几十个。

后果：**刷新 TLB 时两块都可能有残留项**，一条 `invtlb` 会同时作用于两块。

**一个 TLB 表项装两个页（偶/奇页对）**：

```text
┌─────────────────────────────────────────────┐
│ TLBEHI  ─ 虚拟页号高位 + ASID + 页大小     │
├─────────────────────────────────────────────┤
│ TLBELO0 ─ 偶数页的物理页号 + 属性           │
│ TLBELO1 ─ 奇数页的物理页号 + 属性           │
└─────────────────────────────────────────────┘
         一项覆盖 8 KiB（两个 4 KiB 页）
```

所以"精确刷新"的最小粒度是 8 KiB 的页对，不是 4 KiB。代码里
`TLB_PAIR_SIZE = PAGE_SIZE * 2` 就是这个意思。

**invtlb 指令通过 op 编码选择刷新粒度**：

| op | 效果 | 什么时候用 |
|---|---|---|
| 0x5 | 按 ASID + 虚拟地址精确刷一个 pair | 单页 COW/fault |
| 0x4 | 按 ASID 刷所有非全局项 | 大范围修改、drop ASID |
| 0x3 | 清本核所有非全局项 | ASID 用完回绕时 |
| 0x1 | 清本核全部（含全局） | 内核共享映射变了 |

**旧代码用错了 op**。它传了地址给 `invtlb 0x4`，但 0x4 只按 ASID 匹配，地址
操作数不参与匹配。结果：看起来像"刷一页"，实际清空了整个 ASID 的所有热翻译。

**ASID（Address Space Identifier）**。TLB 项带一个 10 位标签标识所属进程，
切进程不用全刷 TLB。LoongArch 的 ASID 是 per-hart 分配的——同一个进程在不同核上
编号可以不同。ASID 0 保留给内核（PLV 0 特权级）。

**DMW（直接映射窗口）**。内核用 `CSR.DMW0..3` 配置一段虚拟地址直接映射物理内存，
不经过页表也不占 TLB。所以内核的线性映射零 TLB 开销——这跟 RISC-V 内核映射也走
页表、也占 TLB 完全不同。

**tlbsrch / tlbrd / tlbwr / tlbfill 四条指令**：
- `tlbsrch`：用 TLBEHI 去 TLB 里找匹配项，索引写入 `CSR.TLBIDX`；
- `tlbrd`：把 TLBIDX 指向的表项读到 CSR；
- `tlbwr`：把 CSR 内容写到 TLBIDX 指向的位置（指定位置覆盖）；
- `tlbfill`：把 CSR 内容填入 TLB，**硬件自己选位置**。

TLB refill 异常用 `tlbfill`（硬件替换策略）。如果错用 `tlbwr` 可能覆盖别的
有效项。

**跨核 TLB shootdown**。一个核修改了页表，别的核的 TLB 里可能还缓存着旧条目。
RISC-V 有 SBI RFENCE（一条 ecall，固件帮你发 IPI 并等确认）。LoongArch 没有
这层固件，必须自己：填 IPI 请求 → 发送 IOCSR IPI → 等目标核执行 invtlb 并
回写 ack → 全部确认后才释放旧物理页。

**TLB 容量探测**。`CSR.PRCFG3` 是只读的硬件配置寄存器，报告 MTLB 项数和 STLB
的组数×路数。本项目从中计算出"精确刷新划不划算"的阈值：页对总数超过
`(MTLB + STLB) / 8` 时就退化为按 ASID 整体刷，因为逐条 invtlb 的成本已经
超过全刷。

## 如何发现

历史遗留问题，属于早期 todo list 项目。QEMU 创建了多个 vCPU 但内核只使用启动核，
多核测试直接卡住。TLB 刷新问题在实现 SMP 后通过用户地址异常和 perf 计数暴露。

## 怎么解决

**启动路径**：从 FDT `/cpus` 解析出 present mask，通过 IOCSR mailbox 写入入口
地址并发送 boot IPI 唤醒从核。每个从核完成独立的栈、MMU、trap、timer、IPI 初始化
后才发布 online bit。

**TLB shootdown 改为批量精确失效**：一次内存管理操作内的所有 PTE 修改合并后
统一提交，每个远端 hart 最多发送一次 IPI。

|  | LoongArch | RISC-V |
|---|---|---|
| 合并粒度 | 8 KiB pair | 4 KiB 单页 |
| 区间表示 | 最多 8 个不相交区间 | 单个 min/max 包络 |
| 降级阈值 | 运行时探测 TLB 容量 | 固定 64 页 |
| 远端失效 | 请求矩阵 + IPI + 自旋等 ack | 一次 SBI RFENCE ecall |
| 目标掩码 | `active_harts`（在用户态的核） | `resident_harts`（住过就算） |
| ASID | 每 hart 一套，发 `target_asids[]` 数组 | 全局一个，必须统一否则退化 |

**active_harts 优化**：只向当前正在用户态执行该地址空间的核发 IPI。不在用户态的
核已经切到内核 ASID 0，旧条目匹配不上；退休它的 context 后下次回来会分配新 ASID，
旧条目永远不会再被选中。比无条件广播所有核少发大量 IPI。

Linux 对照为 `arch/loongarch/kernel/smp.c`、`arch/loongarch/mm/tlb.c` 和
`mm_cpumask()`。CongCore 用固定掩码和 mailbox 请求矩阵代替 Linux 的通用
`smp_call_function_many()`，但保留"只通知相关核心、按范围失效、确认完成后再复用
物理页"的关键语义。

RISC-V 有 SBI RFENCE 扩展，`shootdown_range`（`arch/riscv64/mm/asid.rs:379`）直接：

```rust
let ret = if let Some(asid) = uniform_target_asid(ctx, remote) {
    crate::sbi::remote_sfence_vma_asid(remote, start, size, asid)
} else {
    crate::sbi::remote_sfence_vma(remote, start, size)
};
assert_eq!(ret.error, 0, "remote RISC-V TLB range fence failed");
```

一条 ecall，固件负责把 IPI 发出去、等远端做完、返回。**ecall 返回就等于所有 ack 已到**，内核侧既没有请求槽也没有自旋循环。LoongArch 没这层固件，`TLB_SHOOTDOWN_REQUESTS[target][source]` 矩阵、sequence/ack 配对、`shootdown_tlb` 里那个 `loop { service_pending_tlb_shootdowns(); ...检查 ack... }`（`arch/loongarch64/mod.rs:500`）全都是在手工重造 RFENCE。


## 8 KiB pair 是硬件决定的

LoongArch 的 TLB 表项存的是**偶/奇页对**，一条 `invtlb 0x5` 一次作废一个 pair。所以 `TLB_PAIR_SIZE = PAGE_SIZE * 2`，`record_range` 按 pair 对齐、`local_flush_tlb_range` 按 pair 步进（`asid.rs:560`）——按 4 KiB 走就是白发一半指令。

RISC-V `sfence.vma addr, asid` 是单页刷新 刷新包含addr的页面。

## 区间 vs 多个pair对 

LoongArch 的 `UserTlbInvalidationBatch` 带 `ranges: [(usize, usize); 8]`，`record_range` 会做插入排序 + 吞掉所有重叠区间，超过 8 个才升级 full_mm。

RISC-V 只有 `start`/`end` 两个字段，`record_range` 就是 `start.min()` / `end.max()`。原因很直接：SBI RFENCE 的接口只收一个 `(start, size).

  └─────────┴────────────┴────────────────────────────────┘

  MTLB / STLB

  - MTLB = Multiple Page Size TLB，多页大小
  TLB，全相联。每项自带页大小字段，所以能混装 4 KiB 和 2 MiB 的映射。
  

  - STLB = Single Page Size TLB，单页大小 TLB，组相联。全表只用一种页大小（由
  CSR.STLBPS 设定）。
  
  备忘录：全相连，一次性根所有比较，组相连，多路。
  

LoongArch 从 `PRCFG3` 读 MTLB 项数和 STLB 的 sets×ways，取 `(mtlb + sets*ways) / 8` 作为本核上限，再对所有 hart 取 `min`（`small_range_limit()`）。单位是 pair 数。也就是说降级点跟着硬件 TLB 容量走——逐条 invtlb 的总数不该超过整表的 1/8，否则整表刷更便宜。

## ASIDE 多个核心 

**RISC-V** `shootdown_and_retire_context`：mm 只有**一个**全局 context，所以先 `ctx.context.store(0)` 无效它，然后本地 `sfence.vma zero, asid` + 一次 `remote_sfence_vma_asid(remote, 0, usize::MAX, asid)`。这里有个约束：`uniform_target_asid()` 要检查所有目标 hart 是否**恰好持有同一个 ASID**，不统一就只能退化成不带 ASID 的 `remote_sfence_vma`，把所有非全局项一起作废。

**LoongArch** 的 ASID 是 **per-hart 分配**的（`NEXT_USER_ASID: [AtomicUsize; MAX_HARTS]`，注释写明对齐 Linux 的 per-CPU ASID cache），同一个地址空间在不同核上编号可以不同。所以 `commit_full_mm` 把 `hart_contexts[]` 逐个 swap 出来拼成 `target_asids[MAX_HARTS]` 数组一起投递，每个核用自己那个 ASID 做 `invtlb 0x4`。不存在"ASID 不统一就退化"这回事。


## asid context 设计不同

先看两边有哪些掩码
  
  LoongArch 的 AsidContext 只有两个字段（arch/loongarch64/mm/asid.rs:47）：
  
  pub struct AsidContext {
      hart_contexts: [AtomicUsize; MAX_HARTS],   // 每核 (generation << 10) | asid
      active_harts: AtomicUsize,                  // 正在用户态跑这个 mm 的核
      invalidation_sequence: AtomicUsize,
  }
  
  RISC-V 多两个（arch/riscv64/mm/asid.rs:44）：
  
  pub struct AsidContext {
      context: AtomicUsize,                       // 全局唯一的 ASID context
      hart_contexts: [AtomicUsize; MAX_HARTS],
      resident_harts: AtomicUsize,                // ← 多这个
      active_harts: AtomicUsize,
      invalidation_sequence: AtomicUsize,
      icache_stale_mask: AtomicUsize,             // ← 和这个
  }
  
  resident_harts 是 LoongArch 完全没有的概念。为什么？
  
  根本原因：陷入内核那一刻做的事不一样
  
  LoongArch 的 trampoline 在进内核前就把 PGD 和 ASID
  都切成内核的了。leave_user_asid 的注释写得很明确：
  
  │ The trampoline has already switched to kernel page tables and ASID 0 before
  Rust reaches this call, so an invalidator may safely omit this hart after the bit
  is cleared.
  
  trap_handler 开头的注释也再说了一遍：「The trampoline has already selected kernel
  PGD/ASID 0」。
  
  后果很关键：CSR.ASID 一旦变成 0，硬件在查 TLB
  时就不可能匹配上用户的非全局表项了——ASID
  不等，比较器直接不认。那些脏项还物理地躺在 TLB 里，但已经完全不可达。
  
  RISC-V 不切。leave_user_satp 的注释：
  
  │ The trampoline has trapped out of userspace. The user SATP may remain installed
  while the kernel runs, so the hart stays in resident_harts and is still included
  in page-table shootdowns.
  
  这是个刻意的优化（内核映射作为 global 表项存在于每个根页表里，所以不切 SATP
  也能跑内核代码，省掉一次 SATP 写 + 一次
  sfence.vma）。代价就是：内核态期间这个核还在用户地址空间里，TLB
  里的用户翻译活着、能用，而且硬件还可能继续从页表里重填新的。
  
  shootdown_and_retire_context 里那段注释把这个约束说透了：
  
  │ A remote hart may continue executing this mm after the synchronous RFENCE and
  refill from the now-current PTEs; retaining it in the footprint ensures a
  following page-table edit still targets it before its next trap.
  
  所以 RISC-V 侧「住过就得一直算着」，resident_harts
  一旦置位在这条路径上就不清（只有 active_harts 在陷入时清，那个是给 fence.i 和
  icache 用的）。
  commit_ranges 的四个分支
  
  有了上面的前提，再看 LoongArch
  那段循环（asid.rs:265）。它对每个核做三件事的判断：
  let context = self.ctx.hart_contexts[hart_id].load(Ordering::Acquire);
  let current_generation = ASID_GENERATION[hart_id].load(Ordering::Acquire);
  let context_valid = context_asid(context) != KERNEL_ASID
      && context_generation(context) == current_generation;
  let active = active_harts & (1usize << hart_id) != 0;
  
  context_valid = 这个核给本 mm 分配过一个真实用户 ASID，且 那个 ASID 所属的
  generation 还没被回绕作废。四种组合：
  
  ┌───────────────┬────────┬─────────────────────────────────────┐
  │ context_valid │ active │ 动作                                │
  ├───────────────┼────────┼─────────────────────────────────────┤
  │ ✗             │ ✓      │ commit_full_mm() 兜底后 return      │
  ├───────────────┼────────┼─────────────────────────────────────┤
  │ ✗             │ ✗      │ 清掉 context，跳过                  │
  ├───────────────┼────────┼─────────────────────────────────────┤
  │ ✓             │ ✓      │ 加入 targets，发 IPI                │
  ├───────────────┼────────┼─────────────────────────────────────┤
  │ ✓             │ ✗      │ 退休 context，不发 IPI ← 你问的那个 │
  └───────────────┴────────┴─────────────────────────────────────┘
  
  第一种是最凶的情况：核在用户态跑着这个 mm，但我们不知道它用的是哪个
  ASID（generation 已经回绕，编号可能被别的地址空间抢走了）。这时候按 ASID
  精确失效可能打错对象，只能退化成整体作废。
  
  那个 else 分支为什么安全
  
  } else {
      // This hart is already on kernel ASID 0. Retire its user
      // context instead of interrupting it; the stale hardware ASID
      // will never be selected again.
      self.ctx.hart_contexts[hart_id].store(0, Ordering::Release);

  进到这里的条件是：这个核给本 mm 分配过有效 ASID（比如
  7），但它现在不在用户态。它的 TLB 里可能有 ASID=7 的脏项。三步论证：
  
  第一步，现在够不着。 它当前 CSR.ASID = 0，ASID=7
  的非全局项匹配不上。内核态执行期间绝对安全。
  
  第二步，store(0) 断了将来的路。 它下次要回用户态时会走 prepare_user_asid：

  let context =

  generation {
          cached                                    // 复用

          let (asid, generation, wrapped) = allocate_user_asid(hart_id);   //

          ...

  我们刚把 cached 写成 0，context_asid(0) == KERNEL_ASID，条件不成立 → 走 else
  分支重新分配一个新 ASID。NEXT_USER_ASID[hart_id] 是单调 fetch_add，新号必然不是

  第三步，所以 ASID=7 的脏项永远等不到有人来查它。 它会一直躺在 TLB
  里，直到被正常的容量替换挤掉——这就是注释里 "the stale hardware ASID will never be
  selected again" 的意思。脏数据存在，但不可达，等价于不存在。

  }
  // 号用完了
  let generation = next_generation(hart_id);          // generation++
  NEXT_USER_ASID[hart_id].store(FIRST_USER_ASID + 1, Ordering::Release);
  crate::perf::record_tlb_asid_wrap();
  (FIRST_USER_ASID, generation, true)                  // wrapped = true
  
  三个动作一起完成：
  
  1. generation++ → 所有旧 hart_contexts 里存的 context 一次性全部变成
  context_valid == false，谁都别想复用
  2. 编号从头开始
  3. 返回 wrapped = true
  
  那个 wrapped 会沿着 prepare_user_asid 的 need_flush 一路传到
  trampoline，让它在返回用户态前执行 invtlb 0x3（清掉本核所有非全局项）。所以 7
  号被再次发出去的那一刻，本核 TLB 里所有旧用户项已经被清干净了。
  
  为什么本核要无条件包含
  
  注意 targets 的条件是 hart_id == local_hart || active:
  
  if hart_id == local_hart || active {
      targets |= 1usize << hart_id;
      target_asids[hart_id] = context_asid(context);
  }
  
  本核此刻同样在内核态（CSR.ASID = 0），按上面的逻辑好像也可以退休 context
  走人。但不行——本核是这次修改的执行者，它马上就要返回用户态继续跑这个 mm。如果退休
  context，它会重新分配一个新 ASID，等于每次系统调用改一次页表就换一次 ASID，把 TLB
  里所有还有效的翻译全废掉。远端核不 active 说明它短期内不打算回到这个
  mm，退休的代价可以忽略；本核不是。
  
  所以本核走的是精确失效路径——在 shootdown_tlb 里不走请求槽和 IPI，直接内联
  invtlb：
  if targets & local_bit != 0 {
      match kind {
          TLB_REQUEST_USER_RANGES => {
              for &(start, end) in ranges {
                  mm::local_flush_tlb_range(target_asids[source_hart], start, end);
              }
          }
          ...
      }
  }
  
  收益
  
  对一个不 active 的远端核，这个 else 分支省掉的是：一次 IOCSR_IPI_SEND
  写、目标核一次中断陷入、一轮 sequence/ack 往返、以及发起方为等这个 ack
  而多转的自旋。
  
  而且省掉的不只是延迟——是不打断它。那个核可能正在跑别的进程或处理别的中断，一次
  shootdown IPI 会污染它的流水线和 cache。LoongArch 因为没有 SBI RFENCE、shootdown
  全靠自己做，这笔开销比 RISC-V 上大得多，所以值得为它专门加这一层判断。RISC-V
  那边远端失效由固件代劳、成本低，加上 resident_harts
  的语义本来就不允许跳过，就没做这个优化。
  
  代价是那个核下次回用户态要重新分配 ASID、TLB
  从零重填。这是拿"将来可能发生的重填"换"现在确定发生的 IPI 中断"——赌的是不 active
  的核短期内不会回到这个地址空间。

## 两处相同、一处只有 RISC-V 有

相同的是 odd/even invalidation sequence（编辑 PTE 期间用 seqlock 挡住别的核提交 ASID）和 `deferred_frames` 延后释放——它们在共享层 `PageTableUpdateBatch`（`mm/memory_set.rs:79`）里，两个架构走同一套。屏障实现不同：RISC-V 是 `fence(SeqCst)` + `fence rw, rw`，LoongArch 是 `dbar 0`，且注释特意点明弱序下 active-mask 协议需要的是 StoreLoad 屏障。

只有 RISC-V 有的是第三样东西：`mark_icache_stale` / `fence.i` 远程通知。`PageTableUpdateBatch::mark_icache_stale` 整个函数体裹在 `#[cfg(target_arch = "riscv64")]` 里，LoongArch 上是空操作。


Linux LoongArch 的 `arch/loongarch/kernel/smp.c`、`arch/loongarch/mm/tlb.c` 和
`mm_cpumask()` 提供相同边界。CongCore 用固定掩码和 mailbox 请求矩阵代替 Linux 的
通用 `smp_call_function_many()`，但保留“只通知相关核心、按范围失效、确认完成后再
复用物理页”的关键语义。

本批次把 LoongArch 从“QEMU 创建了多个 vCPU，但内核只使用启动核”推进到一条
完整的 SMP 路径：

```text
FDT 发现 CPU
    -> IOCSR mailbox 唤醒二级核
    -> 每 hart 初始化 MMU/trap/timer/IPI
    -> 发布 online mask
    -> 每 hart 进入调度器
    -> reschedule IPI 唤醒和抢占
    -> ASID + 跨核 TLB shootdown 保证共享页表一致性
```

“二级核打印 online”不是完成标准。多核真正可用还要求启动协议、初始化顺序、
调度、跨核中断和内存管理形成闭环。尤其是页表修改：一个 hart 更新 PTE，并不
代表其他 hart 已经看见新映射；其他 hart 的 TLB 中可能继续保留旧权限、旧物理
页或已经解除的映射。

最保守的 TLB 处理方法是每次修改 PTE 都通知所有 CPU，并刷新整个用户 TLB。
它容易保证正确性，却把一个 4 KiB 页的 COW fault、一次小范围 `mprotect`，
甚至同一 syscall 内连续修改的多个 PTE，都变成昂贵的同步跨核操作。

本批次参考 Linux LoongArch 的 ASID 与 TLB range flush 策略，把原来的粗粒度
路径改造成：

> 单页精确失效，小范围逐页对失效，大范围才 drop ASID；同一页表更新事务中的
> 多个修改合并后，每个远端 hart 最多发送一次 IPI。

这项改动首先保证多核页表一致性，同时缩小 TLB 失效范围、减少 IPI 次数和无效
TLB refill。实现位于 LoongArch SMP 工作树，尚未形成正式提交。

## 1. 先明确 LoongArch 的启动模型

RISC-V 可以通过 SBI HSM `hart_start` 启动其他 hart，也可以调用 SBI remote
fence。LoongArch QEMU `virt` 机器不是这套接口，不能直接复用 RISC-V 路径。

QEMU direct boot 时，二级 vCPU 停在 boot ROM。启动核需要：

1. 把二级核入口地址写入目标 CPU 的 IOCSR mailbox 0；
2. 入口地址为 64 位，因此分别发送高、低 32 位；
3. 执行内存屏障，确保 mailbox 内容先于启动通知可见；
4. 通过 `IOCSR_IPI_SEND` 发送 bit 0 `SMP_BOOT_CPU`；
5. boot ROM 取出入口并跳转到内核 `_start`。

Linux LoongArch 也使用 mailbox 0 和 boot IPI 完成这段协议。当前
`arch::hart_start()` 按相同布局构造 `IOCSR_MBUF_SEND`：

```text
boot hart
   │
   ├─ mailbox[secondary] <- high32(_start)
   ├─ mailbox[secondary] <- low32(_start)
   ├─ dbar 0
   └─ IPI action bit 0
                         │
secondary boot ROM      ▼
                    jump _start
```

实现集中在：

- `os/src/arch/loongarch64/mod.rs`
- `os/src/arch/loongarch64/csr_defs.rs`
- `os/src/main.rs`

## 2. 从 FDT 发现真实 CPU 拓扑

旧代码按 `0..MAX_HARTS` 假定所有 CPU 都存在。这在固定 QEMU 参数下可能工作，
但只要 `-smp` 数量变化，就会向不存在的 hart 发送启动请求，或者让数组容量与
硬件数量不一致。

启动核现在解析 FDT `/cpus` 节点，构造基于物理 hart ID 的
`present_mask`：

```text
HartTopology
 ├─ present_mask   FDT 中存在且内核支持的物理 hart
 ├─ discovered     FDT 中发现的 CPU 总数
 └─ ignored        超出 MAX_HARTS 或位图宽度的 CPU 数
```

这里刻意保留物理 ID，而不是把它们重新压缩为逻辑编号。mailbox、IPI 目标和
`CSR.CPUID` 都使用物理 ID，提前重编号会让“调度器认为的 CPU 1”和“硬件收到
IPI 的 CPU 1”产生歧义。

异常情况下采用保守回退：

- DTB 地址为空或解析失败时，只启用 boot hart；
- 无有效 CPU 节点时，只启用 boot hart；
- boot hart 始终被加入 `present_mask`；
- 超出容量的 CPU 被计数并忽略，不允许越界访问 per-hart 数组。

决赛 LoongArch QEMU 配置最多使用 12 个 vCPU，因此 `MAX_HARTS` 提升为 12。
这个常量同时约束 early stack、processor、runqueue、timer、IPI request、
ASID context 等结构，避免不同子系统各自保留 4、8、12 等不一致上限。

拓扑发现位于 `os/src/mm/dtb.rs`。

## 3. 每个 hart 必须有独立的 early stack

所有 CPU 都从同一个 `_start` 进入，但不能共用启动栈。入口先读取
`CSR.CPUID`，再按物理 hart ID 选择 64 KiB 的独立区域：

```text
sp(hart) = boot_stack_top - hart_id * 64 KiB
```

汇编中的栈总大小不再写死为 4 核，而是由 Rust `global_asm!` 把
`config::MAX_HARTS` 传入：

```text
.space 64 KiB * MAX_HARTS
```

在计算栈地址前还会检查 `hart_id < MAX_HARTS`。不支持的 hart 留在
`idle 0` 循环，不能用越界栈进入 Rust。这个检查必须发生在任何栈访问之前，
否则一个意外启动的高编号 CPU 可以直接覆盖 BSS 或其他 hart 的栈。

对应文件为 `os/src/entry_loongarch.S`。

## 4. 启动屏障与每 hart 初始化

全局对象只能由 boot hart 初始化一次，而大量 CSR 又必须在每个 hart 上分别
设置。实现把启动过程拆成三个阶段：

```text
BOOT_HART_INITED
    选出唯一 boot hart
          │
          ▼
BOOT_BSS_CLEARED
    boot hart 已清理 BSS
          │
          ▼
BOOT_GLOBAL_INIT_DONE
    堆、页表、设备和全局调度状态可用
```

boot hart 执行：

1. 清理 BSS；
2. 解析 FDT，发布 `present_mask`；
3. 初始化物理内存、堆和共享内核页表；
4. 初始化本地 MMU、trap、timer 和 IPI；
5. 用 release store 发布 `BOOT_GLOBAL_INIT_DONE`；
6. 按 `present_mask` 唤醒二级 hart；
7. 等待期望的 online mask，超时打印缺失位图；
8. 创建 init task 并进入调度器。

二级 hart 用 acquire load 等待屏障，随后执行自己的本地初始化：

- 安装共享内核页表根；
- 配置 CRMD paging 状态；
- 设置 TLB refill 入口；
- 配置 STLB 页大小和 page-walk CSR；
- 初始化本地 ASID/TLB 容量信息；
- 安装 trap 入口；
- 启用本地 timer 与 IPI；
- 设置下一次时钟事件；
- 最后才设置 online bit 并进入自己的 scheduler loop。

这里“最后才 online”很重要。调度器只能把任务放到已经具备页表、异常入口、
timer 和 IPI 能力的 hart，否则用户态可能被调度到一个尚未完成初始化的 CPU。

启动核等待 secondary 的最长时间为 5 秒。超时不会静默卡死，而会输出：

```text
expected mask
online mask
missing mask
```

这让 mailbox 失败、入口失败和某个 hart 初始化卡住可以被区分。

## 5. 每 hart 调度器、runqueue 与 idle

二级核启动后不能进入一个空循环；每个 hart 都需要独立的调度上下文。调度层
已经按 `MAX_HARTS` 维护：

- `PROCESSORS[hart]`
- per-hart ready queue
- `NEED_RESCHED[hart]`
- per-hart timer/clockevent 状态
- 当前运行任务与 `on_cpu` 归属

boot hart 只初始化一次 `INITPROC`，secondary 直接调用
`task_start_secondary()` 进入自己的 idle/scheduler loop，避免多个 CPU 重复
创建 init 进程。

任务入队时只在 `online_hart_mask` 与 affinity 的交集中选择目标。新任务会在
允许的在线 hart 中分散；wakeup 尽量保留上次运行 CPU 的局部性，必要时再迁移。
如果任务被放入远端空队列，或它应该抢占远端当前任务，发送 reschedule IPI。

远端处理后设置调度条件，真正的抢占发生在安全点：

- timer tick；
- syscall 返回；
- trap 返回用户态前的 `NEED_RESCHED` 检查；
- 当前任务主动阻塞或让出。

空闲 hart 原来使用 `spin_loop()` 忙等，现在打开中断后执行 LoongArch
`idle 0`。timer 或 IPI 会唤醒它，再回到 scheduler 顶部检查 ready queue。
这既降低无任务时的 CPU 占用，也让“远端入队 + IPI kick”形成完整唤醒路径。

## 6. IPI action 与用户可见的 SMP 语义

IOCSR IPI action 位与 Linux LoongArch 的基本分类对齐：

| 位 | 名称 | 当前用途 |
| ---: | --- | --- |
| 0 | `SMP_BOOT_CPU` | 从 QEMU boot ROM 唤醒二级核 |
| 1 | `SMP_RESCHEDULE` | 唤醒 idle hart 或请求远端重新调度 |
| 2 | call-function 类动作 | 执行待处理的 TLB shootdown |

每个 hart 都会启用 ECFG 的 IPI local-enable 位和 IOCSR IPI enable。handler
先清除硬件 pending action，再处理软件请求，避免旧 pending 位导致重复陷入。
IPI 在用户态和允许嵌套中断的内核路径中都能被处理。

用户态看到的 CPU 语义也与真实 online mask 连接：

- `sched_getaffinity` 只返回在线且允许的 CPU；
- `sched_setaffinity` 更新任务允许集合并触发必要迁移/重调度；
- `getcpu` 返回当前物理 hart；
- `/proc` 中的 CPU 与中断信息按 online hart 输出；
- `getcpu01` 在 12 核运行中实际观察到 CPU 11，而不是始终返回 CPU 0。

到这里，多核已经具备“发现、启动、调度、唤醒、用户可见”的基本能力。下一部分
解决多 hart 共享地址空间后最关键的内存一致性问题。

## 7. 原问题为什么会影响多核性能

一次页表更新需要完成两件不同的事情：

1. 把新 PTE 写入内存；
2. 让所有可能缓存旧翻译的 hart 丢弃对应 TLB 项。

如果只做第一步，同一地址空间的另一个线程仍可能：

- 在 `mprotect(PROT_READ)` 后继续使用旧的可写翻译；
- 在 COW 替换物理页后继续访问旧页；
- 在 `munmap` 后继续访问已经释放、甚至已经被复用的物理页；
- 因为保留旧的只读项而产生重复写异常。

旧路径还有一个 LoongArch 指令语义问题：它把地址传给了 `invtlb 0x4`。但
操作码 `0x4` 只按 ASID 匹配，地址操作数不参与匹配。因此代码看起来像“刷新
一页”，实际上会丢弃该 ASID 的全部非全局项。

于是一次修改多页的 syscall 可能退化为：

```text
修改 PTE 0 -> drop 整个 ASID -> IPI -> 等待 ack
修改 PTE 1 -> drop 整个 ASID -> IPI -> 等待 ack
修改 PTE 2 -> drop 整个 ASID -> IPI -> 等待 ack
...
```

性能损失不只来自 `invtlb` 指令本身，还包括：

- 每次同步 IPI 的发送、陷入和返回；
- 发起 hart 等待所有目标 hart 确认；
- 目标 hart 被迫中断当前工作；
- 整个 ASID 的热 TLB 项被清空，后续访问重新 page walk；
- 多个 hart 同时修改同一 mm 时产生同步放大。

对单核或短测试，这种代价不一定明显；对共享地址空间、多线程 allocator、
频繁 COW、`mprotect`/`munmap` 和并行编译场景，它会进入热路径。

## 8. LoongArch 的精确失效粒度

LoongArch 一个普通 TLB 项包含偶数页和奇数页两个 `TLBELO`，在当前 4 KiB
页配置下，一个 TLB 项覆盖相邻的 8 KiB 页对。因此“单页精确失效”的硬件实际
粒度是包含该页的 8 KiB TLB 页对，而不是任意单个 4 KiB 半项。

本实现使用以下操作：

| 操作码 | 匹配范围 | 使用场景 |
| --- | --- | --- |
| `0x5` | 非全局项，ASID + 虚拟地址 | 单页和小范围用户映射 |
| `0x4` | 非全局项，ASID | 大范围用户映射，drop ASID |
| `0x3` | 当前 hart 的全部非全局项 | 本地 ASID generation 回绕 |
| `0x1` | 当前 hart 的全部 TLB 项 | 共享内核映射发生变化 |
| `0x6` | 全局项，或匹配 ASID + 地址 | 低层页表 API 的当前地址失效 |

记录区间时，起止地址都按 8 KiB 页对扩展：

```text
pair_start = align_down(start, 8 KiB)
pair_end   = align_up(end, 8 KiB)
pair_count = (pair_end - pair_start) / 8 KiB
```

所以修改一个 4 KiB PTE 时只执行一次地址精确的 `invtlb 0x5`，不会再清空
该进程的其他热翻译。

对应代码主要位于：

- `os/src/arch/loongarch64/csr_defs.rs`
- `os/src/arch/loongarch64/mm/asid.rs`
- `os/src/arch/loongarch64/mm/page_table.rs`

## 9. 单页、range 与 drop ASID 的分界

逐页对执行 `invtlb` 并不总是最优。范围足够大时，一次按 ASID 失效比执行数百
次地址失效更便宜；过大的失效消息也不适合放进固定大小的无锁 IPI payload。

每个 hart 初始化时从 `PRCFG3` 探测 MTLB/STLB 组织，计算精确失效的容量截止
值。策略与 Linux LoongArch 保持一致：

- 只有 MTLB 时，精确失效上限取总容量的 `1/2`；
- 同时存在 STLB 时，上限取总容量的 `1/8`；
- 系统使用各在线 hart 探测值中的最小值，保守覆盖可能不同的 CPU 配置；
- 合并后超过 8 个离散区间，或页对总数超过截止值时，退化为 drop ASID。

最终决策大致是：

```text
                     PTE 修改
                        │
                        ▼
              对齐到 8 KiB TLB 页对
                        │
                        ▼
               合并重叠和相邻区间
                        │
           ┌────────────┴────────────┐
           │ ranges <= 8 且           │ 否
           │ pairs <= TLB cutoff      ├─────────┐
           └────────────┬────────────┘         │
                        │ 是                    ▼
                        ▼                 retire context
              ASID + address 精确失效       + invtlb 0x4
```

这不是固定用页数猜测，而是根据 CPU 实际 TLB 容量选择成本较低的路径。典型
结果是：

- 4 KiB COW/fault：一次 8 KiB 页对失效；
- 64 KiB `mprotect`：一个合并 range，循环失效少量页对；
- 4 MiB `mprotect`：超过阈值，直接 drop ASID。

## 10. 用页表更新事务合并多个修改

只优化 `invtlb` 操作码还不够。如果 `munmap` 每删一个 PTE 就立即提交一次
shootdown，IPI 次数仍然与页数成正比。

为此，LoongArch 的 `MemorySet` 增加了 `PageTableUpdateBatch`。它以一次内存
管理操作为事务边界，记录：

- 被修改的单页或区间；
- 合并后的最多 8 个 range；
- 修改 PTE 的总次数；
- shootdown 完成前不能释放的旧 `FrameTracker`；
- 是否包含必须全 TLB 失效的共享内核映射。

相邻或重叠区间在记录时立即合并。例如同一 syscall 依次修改：

```text
[0x1000, 0x2000)
[0x2000, 0x3000)
[0x5000, 0x6000)
```

按 TLB 页对对齐后可合并为更少的区间，最后只提交一次 shootdown。事务的
`commit` 和 `Drop` 都会完成失效，避免错误返回路径漏掉提交。

当前已经接入的路径包括：

- `mprotect`
- `munmap`
- `madvise`
- `mremap`
- fork 时建立 COW
- COW 写异常
- lazy fault
- shared mapping 更新
- 内核栈移除

因此“一个 syscall 内多次修改页表”不再等于“发送多次 IPI”。远端 IPI 数量
主要由真正运行该 mm 的 hart 数量决定，而不是被修改的 PTE 数量决定。

## 11. 每 hart ASID 与 active hart 跟踪

硬件 TLB 是 per-hart 资源，因此同一个 mm 不必在所有 hart 上使用同一个
ASID。本实现给每个地址空间保存：

```text
AsidContext
 ├─ hart_contexts[hart] = generation | local ASID
 ├─ active_harts
 └─ invalidation_sequence
```

每个 hart 独立维护 `next_user_asid` 和 `asid_generation`。ASID 0 保留给内核，
可用 ASID 位数从 `CSR.ASID.ASIDBits` 探测。

`active_harts` 表示当前正在用户态执行这个 mm，或处于最终返回用户态窗口的
hart。它让失效路径可以区别处理：

- active hart 可能正在使用旧翻译，必须发送 IPI 并等待确认；
- inactive hart 已经使用内核 ASID 0，不必立即打断，只需退休该 mm 在该 hart
  上的旧 context；
- 该 mm 下次调度到此 hart 时分配新 ASID，旧 TLB 项不会再次被选中；
- 当本地 ASID 空间回绕时，generation 增加，并清空当前 hart 的非全局项，
  防止旧 ASID 被重新使用。

这比无条件向所有 online hart 广播更接近 Linux 的 lazy TLB 思路。CPU 数量
增加时，IPI fan-out 由“全部 CPU”缩小为“确实可能使用旧翻译的 CPU”。

## 12. 失效序号关闭用户态返回竞态

只读取一次 `active_harts` 不足以保证正确性。考虑以下竞态：

```text
hart 0                              hart 1
开始修改页表
读取 active_harts，未看到 hart 1
                                    正准备返回同一个 mm 的用户态
修改 PTE
不向 hart 1 发 IPI
                                    带着旧 ASID 返回用户态
```

实现使用奇偶 `invalidation_sequence` 形成 mm-local 轻量 seqlock：

1. invalidator 把 sequence 从偶数改为奇数；
2. 奇数期间，新的用户态返回不能提交 active bit；
3. 完成 PTE 修改、IPI 和 ack；
4. sequence 恢复为偶数；
5. 与失效并发的返回路径撤销 active bit，重新获取有效 context 后再返回。

这样 `active_harts` 的快照与“谁可以进入用户态使用旧 ASID”形成闭环。该机制
只覆盖一个 mm，不需要全局页表失效锁。

## 13. 无锁 IPI 请求矩阵与一次性通知

TLB shootdown 使用固定的请求矩阵：

```text
requests[target_hart][source_hart]
```

每个 source 独占目标上的一个槽位，槽位包含：

```text
request sequence
ack sequence
kind
target ASID
range count
range[8]
```

发送流程如下：

1. 发起 hart 完成全部 PTE store；
2. `dbar 0` 保证页表写在请求发布前全局可见；
3. 填充每个目标 hart 的 payload；
4. 用 release store 发布新的 request sequence；
5. 每个远端目标只发送一次 bit 2 call-function 类 IPI；
6. 本 hart 直接执行相同的本地失效；
7. 等待所有目标把 ack 更新到本次 sequence。

目标 hart 用 acquire load 读取请求，扫描来自不同 source 的槽位。如果同一时刻
存在多类请求：

- full TLB 请求覆盖其他所有请求；
- user-all 请求覆盖 ASID/range 请求；
- 否则按各 source 的 ASID 和 range 执行精确失效。

独立 source 槽位避免两个 hart 同时发请求时互相覆盖，也不需要一把全局
shootdown 锁。固定数组还避免在 IPI handler 中动态分配内存。

## 14. 两个容易遗漏的并发正确性问题

### 14.1 必须等待 ack 后才能释放旧物理页

`munmap` 或 COW 替换 PTE 后，旧 `FrameTracker` 不能马上 drop。否则可能发生：

```text
hart 0 更新 PTE 并释放旧页
        │
        ├─ 物理页被 allocator 分给其他对象
        │
hart 1 仍通过陈旧 TLB 写入旧物理页
        ▼
新对象内容被破坏
```

`PageTableUpdateBatch` 把旧 frame 保存在 `deferred_frames` 中。只有所有目标
hart 确认完成失效后，才允许这些 frame 进入 allocator，形成：

```text
PTE store -> publish request -> remote invtlb -> ack -> release old frame
```

因此同步等待不仅是性能代价，也是物理页生命周期的正确性边界。

### 14.2 等待 shootdown 时也要服务入站请求

如果 hart 0 和 hart 1 同时修改同一个或不同 mm，可能互相发送 shootdown：

```text
hart 0 等待 hart 1 ack
hart 1 等待 hart 0 ack
```

如果两边只自旋等待，就会形成环路。发送端在等待期间会主动调用
`service_pending_tlb_shootdowns()`，先完成别人发给自己的请求，再继续检查
自己的 ack。

另一个锁序问题发生在共享 `MemorySet` 的 `CLONE_VM` 线程之间：发送者可能
持有 mm 锁等待目标 ack，而目标从用户态进入异常后又先尝试获取同一把 mm 锁。
LoongArch trampoline 此时已经切换到内核页表和 ASID 0，因此 trap handler
现在先处理无锁 TLB 请求并确认，再清除 active bit、获取其他内核锁。这避免了：

```text
sender: holds MemorySet lock -> waits for ack
target: waits for MemorySet lock -> cannot ack
```

普通 syscall 和较长 timer 工作期间也允许 IPI 被及时处理；嵌套 timer 工作则
继续延后，避免重新进入复杂调度路径。

## 17. 与 Linux 的关系和剩余差距

本实现参考了 Linux LoongArch 的以下机制：

- IOCSR mailbox + boot IPI 的 secondary 启动协议；
- reschedule/call-function 类 IPI action；
- per-CPU ASID context；
- 根据 `PRCFG3` TLB 容量选择 range flush 或 ASID flush；
- 通过 call-function 类 IPI 执行远端失效；
- 地址精确的 `invtlb` 操作码。

参考源码：

- [Linux LoongArch SMP 启动与 IPI](https://github.com/torvalds/linux/blob/master/arch/loongarch/kernel/smp.c)
- [QEMU LoongArch direct boot](https://github.com/qemu/qemu/blob/master/hw/loongarch/boot.c)
- [Linux LoongArch TLB 操作定义](https://github.com/torvalds/linux/blob/master/arch/loongarch/include/asm/tlb.h)
- [Linux LoongArch range flush](https://github.com/torvalds/linux/blob/master/arch/loongarch/mm/tlb.c)
- [Linux LoongArch CPU/TLB 能力探测](https://github.com/torvalds/linux/blob/master/arch/loongarch/kernel/cpu-probe.c)

当前实现仍不是 Linux 完整 SMP/MM 子系统：

- CPU 拓扑在启动时静态确定，尚未实现 CPU hotplug/offline；
- 调度器没有 Linux 完整的 sched-domain、NUMA 和周期负载均衡模型；
- IPI bit 2 目前是专用 TLB 请求矩阵，还不是通用
  `smp_call_function_many()` 队列；
- range payload 固定为 8 段，复杂 VMA 编辑会保守退化为 ASID 失效；
- shootdown 仍需同步等待，尚未实现更完整的 lazy-mm、RCU page-table
  reclamation 或异步释放策略；
- 尚缺 BuildStorm 前后对照数据和真实 Loongson 硬件验证；
- LoongArch LSX 上下文仍未实现，相关用户程序端到端门禁需要单独处理。

这些限制不影响本批次的核心语义：小修改不再无条件清空整个地址空间，多次 PTE
编辑不会重复发送 IPI，而旧物理页只有在所有相关 hart 确认失效后才会被复用。

# 协议实现的具体细节

核心是arch 下的hart_start函数。 RISC-V 上 hart_start 就是一条 SBI HSM 调用，固件负责把目标核拉起来并返回错误码。LoongArch 没有这层固件，所以 arch::hart_start 自己按 Linux 的 CSR-IPI/mailbox ABI 去操作 IOCSR 寄存器（os/src/arch/loongarch64/mod.rs:548）：往目标核的 mailbox 0 写入入口地址，然后给它发一个 IPI_ACTION_BOOT_CPU。QEMU 的 direct-boot ROM 把辅助
  CPU 停在 VIRT_FLASH0_BASE 的自旋循环里，收到这个 action 后读走 mailbox 0 并跳过去。
  
```rust
  
  pub fn hart_start(hart_id: usize, start_addr: usize, _opaque: usize) -> usize {
      if hart_id >= MAX_HARTS { return 1; }
      let mailbox = 0u64;
      let box_low = mailbox << 1;      // 每个 mailbox 占两个 32 位 box
      let box_high = box_low + 1;
      let cpu = (hart_id as u64) << IOCSR_MBUF_SEND_CPU_SHIFT;   // 目标核编号进
  bit16+
      let data = start_addr as u64;
  
      // 先写高 32 位，再写低 32 位；BLOCKING 位(bit31)让写操作等对端就绪
      iocsr_write64(IOCSR_MBUF_SEND, BLOCKING | (box_high << 2) | cpu | (data &
  H32_MASK));
      iocsr_write64(IOCSR_MBUF_SEND, BLOCKING | (box_low  << 2) | cpu | (data <<
  32));
      memory_barrier();                 // dbar 0，保证地址先落地再响铃
      send_ipi_action(hart_id, IPI_ACTION_BOOT_CPU);
      0
  }
```
  几个细节：
  - 高低半写法直接照搬 Linux 的 csr_mail_send()：IOCSR_MBUF_SEND 是 64 位写口，低
  32 位是控制字段（blocking/box/cpu），要发送的 32 位数据放在 bit32
  以上，所以低半用 data << 32，高半用 data & 0xffff_ffff_0000_0000 直接对齐。

  - 顺序必须是「高半 → 低半 → dbar →
  IPI」。目标核以低半的写入作为地址完整的信号，dbar
  再挡住乱序，避免它读到半个入口地址。

  - send_ipi_action 写 IOCSR_IPI_SEND，值是 BLOCKING | action_index | (cpu <<
  16)。注意 IOCSR_IPI_SEND 收的是 action 索引（boot=0/resched=1/tlb=2），而
  IOCSR_IPI_STATUS 报的是对应的位掩码，csr_defs.rs:75 里把两组常量刻意分开定义。

  - 返回值只有「hart_id 越界返回 1」这一种失败，其余恒返回
  0。因为没有固件应答，真正的失败只能靠上层超时发现。
  
  从核落地之后
  传入的 start_addr 是 _start（main.rs:167），即链接地址
  0x8000_0000。入口汇编（os/src/entry_loongarch.S）做三件事：
  
  1. csrrd $a0, CSR_CPUID 拿物理核号，先跟 MAX_HARTS（LoongArch 为
  12，config.rs:88）比较，越界就 idle 0 停住，绝不去算栈指针。
  2. 按核号在静态数组 boot_stack 里切出各自的 64KB 早期栈（boot_stack_top - id *
  64K）。
  3. 配 DMW0/DMW1 直接映射窗口并跳一次，把 PC 挪到窗口地址，再 bl rust_main。
  
  rust_main(hart_id)（main.rs:355）用 BOOT_HART_INITED 的 CAS
  区分首核和从核，从核走 loongarch_secondary_main。
  
  四段式启动握手
  
  从核和主核之间有四个屏障，都放在 .data 段，避免被 clear_bss 清掉：
  
  ┌──────────────────────────────────────┬──────────────────────────────────────┐
  │ 屏障                                 │ 作用                                 │
  ├──────────────────────────────────────┼──────────────────────────────────────┤
  │ BOOT_BSS_CLEARED                     │ 从核在此之前不能碰任何 .bss          │
  │                                      │ 里的全局量                           │
  ├──────────────────────────────────────┼──────────────────────────────────────┤
  │ BOOT_GLOBAL_INIT_DONE                │ 主核完成堆/页表/日志初始化后才放从核 │
  │                                      │ 进去                                 │
  ├──────────────────────────────────────┼──────────────────────────────────────┤
  │ BOOT_LOONGARCH_READY_HART_MASK       │ 从核完成本地 MMU/trap/timer          │
  │                                      │ 后置位，供主核统计                   │
  ├──────────────────────────────────────┼──────────────────────────────────────┤
  │ BOOT_LOONGARCH_SMP_FINALIZED +       │ 主核冻结 SMP 成员集和                │
  │ ADMITTED_HART_MASK                   │ AT_HWCAP，晚到的核直接 park          │
  └──────────────────────────────────────┴──────────────────────────────────────┘
  
  从核过屏障后的顺序（main.rs:263）刻意对齐 Linux 的 bring-up：bootstrap_init()（配
  PG/PWCL/TLB refill、FP 全关、探测 hwcap 与主频）→ activate_kernel_space() →
  关掉直接映射窗口 → init_trap() → 外部中断 → 定时器 → 置 ready 位 → 等准入 →
  开中断 → mark_hart_online() → 本地 flush_tlb_all → 进调度器。
  
  最后三步的顺序有意为之：先 online 再 flush。一个核只有能接 IPI 之后才可以成为 TLB
  shootdown 的目标；采样到旧掩码的写者排在这次本地 flush
  之前，之后的写者则会把它算进掩码，两边都不会漏。
  
  主核侧 start_loongarch_secondaries（main.rs:161）先把自己的位写进 ready
  mask，逐核调 hart_start，然后用 clock_freq * 5 个 tick 做超时等 ready
  mask；超时不算致命，只是打日志并把没就绪的核排除在准入集之外。之后冻结 hwcap、置
  finalized，再等一轮 online mask，最后才 list_apps() + task_start()。
  
  与 RISC-V 路径的差异
  
  - RISC-V 从核入口是固定的 KERNEL_ENTRY_PA = 0x8020_0000，并且能通过 opaque 把
  dtb_pa 传给从核；LoongArch 的 _opaque 未使用，从核靠固定的 DEVICE_TREE_ADDR =
  0x100000 自己找 FDT。
  - RISC-V 只有 present/started/online 三个掩码；LoongArch 多一层
  ready→admitted，因为它的 bootstrap_init 是逐核执行的（页表配置、hwcap
  交集、主频探测都是 hart-local 的），必须在第一个用户进程读到 AT_HWCAP
  之前把特性交集定住。
  - IPI 的复用方式也不同：LoongArch 用 action 位区分 boot/reschedule/TLB
  shootdown，handle_ipi_interrupt（mod.rs:392）先 clear_ipi_interrupt() 再排空
  shootdown 请求矩阵；boot 那一位在从核 enable_ipi_interrupt() 把 IOCSR_IPI_EN
   打开后被顺带清掉。
  
  一处依赖需要留意：mailbox 0 + IPI_ACTION_BOOT_CPU 这个协议是 QEMU virt ROM
  的行为，代码注释里也点明了。真机固件若用别的 parking 协议，这段得改。
 
## mailbox

Mailbox 是 LoongArch 每个核心 IPI
  单元里的一小块寄存器暂存区，用来在核之间传递数据（区别于只能传"事件"的 IPI）。
   - IOCSR_MBUF_SEND (0x1048) —— 往指定核的指定 box 写 32 位
  - IOCSR_IPI_SEND (0x1040) —— 往指定核置一个 action 位
  

# TLB (loongarch)

## 两块 TLB

内核文档（`Documentation/arch/loongarch/introduction.rst:302`）一句话讲清了结构：

> LoongArch's TLB includes a fully-associative MTLB (Multiple Page Size TLB) and set-associative STLB (Single Page Size TLB).

- **MTLB**：全相联，每个表项自带页大小字段，可以混装 4 KiB / 2 MiB / 1 GiB 等
- **STLB**：组相联，全表统一一个页大小（由 `CSR.STLBPS` 设定，CongCore 写的是 `PAGE_SIZE_BITS`=12）

查表时两块并行查。容量从 `PRCFG3` 读出来——这就是前面说的探测阈值的来源：

```rust
let tlb_type  = config & 0xf;                    // 1 = 只有 MTLB, 2 = MTLB+STLB
let mtlb_size = ((config >> 4)  & 0xff) + 1;     // MTLB 项数
let ways      = ((config >> 12) & 0xff) + 1;     // STLB 路数
let sets      = 1 << ((config >> 20) & 0x3f);    // STLB 组数
```

## 一个表项装两个页

这是 LoongArch TLB 最特别的地方，也是前面「8 KiB pair」的根源。一个表项由三个部分组成：

```
TLBEHI   (CSR 0x11)  ┐ 共享部分：VPN 高位、ASID、G 位、页大小
TLBELO0  (CSR 0x12)  ├ 偶页的 PPN + 属性
TLBELO1  (CSR 0x13)  ┘ 奇页的 PPN + 属性
```

一条表项覆盖一对相邻的偶/奇页，VA 的 bit12（4 KiB 页时）用来在 ELO0/ELO1 之间选。所以：

- 精确失效的最小粒度是 8 KiB，不是 4 KiB → `TLB_PAIR_SIZE = PAGE_SIZE * 2`
- 填表时必须一次填一对，refill 处理器里连着两条 `ldpte` 才 `tlbfill`

`TLBELO` 的字段布局和 PTE 基本一致（`page_table.rs:23`）：

```
bit 0     V      有效
bit 1     D      脏
bit 3:2   PLV    特权级（3 = 用户可访问）
bit 5:4   MAT    内存访问类型（0 强序不缓存 / 1 一致可缓存 / 2 弱序不缓存）
bit 6     G      全局（不参与 ASID 匹配）
bit 7     P      存在
bit 8     W      可写
bit 61    NR     不可读
bit 62    NX     不可执行
bit 63    RPLV   限制特权级
```

注意 NR/NX/RPLV 在最高三位——是「禁止」语义而不是「允许」语义，跟 RISC-V 的 R/W/X 正好相反。bit 9/10 的 `COW`/`SHARED` 是 CongCore 自己借硬件忽略位放的软件标记。

PTE 和 TLBELO 格式一致不是巧合：正因如此 `ldpte` 指令能把内存里的 PTE 直接搬进 TLBELO，不用软件转换。

## TLB miss 是异常，由软件填

这是跟 RISC-V/x86 最大的行为差异。LoongArch 没有全自动的硬件 page walker：TLB 缺失会触发一个**专用的 TLB refill 异常**，跳到 `CSR.TLBRENTRY` 指的处理器（必须 4 KiB 对齐）。CongCore 的实现就是 `tlb_refill.S`：

```asm
__rfill:
    csrwr $t0, TLBRSAVE      # 专用 save 寄存器，不碰通用栈
    csrrd $t0, PGD           # 硬件已按 VA 高低半自动选好 PGDL/PGDH

    lddir $t0, $t0, 2        # 走第 2 级目录
    beqz  $t0, construct_invalid
    ...
    lddir $t0, $t0, 1        # 走第 1 级目录
    ...
    ldpte $t0, 0             # 装偶页 PTE → TLBRELO0
    ldpte $t0, 1             # 装奇页 PTE → TLBRELO1
    tlbfill                  # 一次填入这一对
    ...
    ertn
```

`lddir` / `ldpte` 是硬件辅助的页表访问指令，怎么解码页表由 `PWCL`/`PWCH` 告诉它。CongCore 在 `bootstrap_init` 里配的是三级、4 KiB 页、8 字节 PTE：

```rust
pwcl |= ptbase(12)     << 0;   // PTE 层起始位
pwcl |= dir_width(9)   << 5;
pwcl |= dir1_base(21)  << 10;
pwcl |= dir_width(9)   << 15;
pwcl |= dir2_base(30)  << 20;
pwcl |= dir_width(9)   << 25;
```

即 `12 + 9 + 9 + 9 = 39` 位虚拟地址，跟 RISC-V Sv39 对齐——这也是 CongCore 能在两个架构间复用大部分页表代码的原因。

注意 refill 异常有一整套**独立的** CSR（`TLBRELO0/1`、`TLBREHI`、`TLBRBADV`、`TLBRERA`、`TLBRSAVE`），跟普通异常的 `TLBELO0/1`、`ERA`、`SAVEn` 分开。这样 refill 处理器不需要保存现场，也不会破坏正在处理的普通异常状态——`csrwr $t0, TLBRSAVE` 一条指令就腾出了工作寄存器。

`construct_invalid` 分支处理的是页表根本没建到那一层的情况：填一个 V=0 的无效项进去，让访存重新以普通的 page fault 形式报上来，由 C 代码处理。不这么做的话会 refill 异常反复触发。

## ASID 和失效指令

ASID 10 位（`ASID_MASK = 0x3ff`），实际宽度可以从 `CSR.ASID` 的 bit[23:16] 读——`init_local_tlb_capabilities` 就顺手读了，取和 0x3ff 的交集。CongCore 把 ASID 0 留给内核（`KERNEL_ASID = 0`），用户从 1 开始。

失效用 `invtlb op, asid, addr`，op 决定匹配规则：

| op | 语义 | CongCore 用途 |
|---|---|---|
| 0x0 | 全表清空 | 启动时初始化 |
| 0x1 | 清本核全部 | `local_flush_tlb_all`（内核映射改了） |
| 0x3 | 清所有非全局项 | `local_flush_tlb_user` |
| 0x4 | 按 ASID 清非全局项 | `local_flush_tlb_asid`（降级路径） |
| 0x5 | 按 ASID + 地址清 | `local_flush_tlb_range`（精确路径，一次一个 pair） |
| 0x6 | 按地址清（含全局项） | 内核共享映射的单页失效 |

## 内核映射不占 TLB

最后一个结构性特点：`CSR.DMW0..3` 配的**直接映射窗口**完全绕过 TLB，`VA = PA + 固定偏移`。LA64 下 `XKPRANGE`（`0x8000_0000_0000_0000` 起）就是这么用的，cache 属性由 VA 的 bit[61:60] 选。

所以内核的线性映射一条 TLB 表项都不消耗——这跟 RISC-V 必须把内核也放进页表、内核映射同样占 TLB 是完全不同的。代价是内核想用页表管理自己的地址空间时得主动关窗口，CongCore 里就是 `disable_direct_map_windows()`（`arch/loongarch64/mod.rs:170`）：把 DMW0/DMW1 清零并 `invtlb 0x0`，主核和每个从核在 `activate_kernel_space()` 之后都要做一次。
