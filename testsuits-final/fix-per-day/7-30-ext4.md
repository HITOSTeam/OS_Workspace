# 7-30 ext4 全局串行路径诊断

## 问题概述

历史 ext4 读取或目录操作要连续经过三层串行点：所有文件系统操作共用的
`EXT4_LOCK`、全局块缓存管理器，以及由互斥锁包裹的 VirtIO 块设备。缓存未命中时，
块缓存管理器仍持锁读取设备；VirtIO 请求提交后又在 `can_pop()` 上持续轮询。一个冷块
读取因此可能阻塞其他 inode、其他目录，甚至本可直接命中的缓存访问。

## 如何发现

这份早期记录来自源码审查。当时没有保存独立 `perf.data` 或专用串口日志，因此不能把
CAgent 的文件测试停顿直接归因给某一把锁。历史代码可使用以下命令复核：

```sh
git -C os show 43a786f:src/fs/inode.rs | \
  rg -n 'EXT4_LOCK|with_ext4_lock'
git show 53368b5d^:ext4-fs/src/block_cache.rs | \
  rg -n 'BLOCK_CACHE_MANAGER|read_block|write_block|sync_all'
git -C os show 43a786f:src/drivers/block/virtio_blk.rs | \
  rg -n 'Mutex<VirtIOBlk|read_blocks|write_blocks'
git show 4efa921d^:vendor/virtio-drivers-pci/src/queue.rs | \
  rg -n 'while !self.can_pop|spin_loop'
```

命中结果分别证明：ext4 adapter 只有一个全局入口锁；块缓存未命中和同步路径调用设备；
每个块设备由一把互斥锁保护；旧 VirtIO 队列等待循环会持续检查完成状态。CAgent 当时
卡在 `fs-create`、`fs-directory`、`fs-search`，与该路径相关，但本文没有调用栈或锁
持有者日志，所以只把它列为高可信结构问题，不写成已经证实的唯一根因。

## 怎么解决

正确修复必须同时改变三层锁边界，而不是只删除 `EXT4_LOCK`：

```text
路径层：按 (device_id, inode_num) 找到稳定的 inode 读写锁
缓存层：manager 锁内只预留 Loading；锁外读盘；锁内发布 Ready
设备层：请求对象固定缓冲区；允许多个请求在途；中断完成后唤醒调用者
```

块缓存的核心状态应类似：

```rust
enum CacheSlot {
    Loading(Arc<LoadState>),
    Ready(Arc<BlockCache>),
}
```

第一个未命中者在 manager 锁内插入 `Loading`，释放锁后执行设备读取，最后重新加锁
发布 `Ready`；其他访问者等待同一个 `LoadState`，不会重复读盘，也不会阻塞无关缓存
项。写回同样要先在锁内取得带 generation 的票据，锁外执行设备写入，再锁内确认没有
并发新写后提交 clean 状态。

Linux 的 `i_rwsem`、页缓存锁、块多队列和 VirtIO 完成中断分别承担这些职责。CongCore
没有完整 Linux 块多队列和后台回写线程，因此后续实现采用稳定 inode 锁、
`Loading/Ready` 单次加载、锁外写回和单 VirtQueue 多请求；它复制的是锁边界和对象
生命周期，不是 Linux 的全部内部结构。完整实现和测试见
`7.31-ext4-virtio-concurrency.md`。

## 历史分析背景

这个问题属于跨文件系统、缓存和设备驱动的设计问题。早期实现为了简化正确性使用了
粗粒度锁，因此当时只记录风险，没有直接删除全局锁。

## 问题概述
文件系统访问经过多层全局串行化，并且真正访问磁盘时采用同步自旋等待。

一次普通读操作大致走这条路径：

```text
进程 read/create/stat
        │
        ▼
全局 EXT4_LOCK
所有 hart、所有 ext4 实例共用
        │
        ▼
全局 BLOCK_CACHE_MANAGER
缓存未命中时，持锁读取磁盘
        │
        ▼
VirtIOBlock Mutex
同一块设备一次只能处理一个调用
        │
        ▼
提交 VirtIO 请求
while (!can_pop()) 自旋等待完成
```

### 1. `EXT4_LOCK` 把整个文件系统变成了单通道

历史实现只有一个全局 `EXT4_LOCK`，用于串行化所有 ext4 操作；可在历史版本
`os/src/fs/inode.rs` 中复核。

例如：

- hart 0 正在读取 `/user/a`
- hart 1 想创建 `/tmp/b`
- hart 2 想执行 `stat("/bin/c")`
- hart 3 想遍历另一个目录

即使它们访问不同文件、不同目录，甚至不同 ext4 块设备，也只能依次取得同一把锁。

这把锁已经做了一个不错的改进：竞争者会主动让出 CPU，而不是始终空转。但这只能减少等待时的 CPU 浪费，不能增加并发度。

所以八核情况下，CPU 计算可以并行，但 ext4 核心操作仍近似：

```text
hart0: [文件操作 A]
hart1:              [文件操作 B]
hart2:                           [文件操作 C]
```

而不是：

```text
hart0: [文件操作 A]
hart1: [文件操作 B]
hart2: [文件操作 C]
```

### 2. 缓存未命中会把磁盘等待包含在锁内

ext4 有一个全局块缓存管理器。问题是，缓存未命中时，它会在持有管理器锁的情况下调用
块设备读取；可在 `53368b5d^` 版本的 `ext4-fs/src/block_cache.rs` 中复核。

也就是说：

```text
获取 BLOCK_CACHE_MANAGER
    ├── 查缓存
    ├── 缓存未命中
    ├── 同步读取磁盘       ← 管理器锁仍未释放
    ├── 插入缓存
    └── 释放管理器锁
```

结果是：一个任务正在读取未缓存的数据时，其他任务可能连已有缓存块的查询都进不去。

缓存淘汰或全量 `sync` 时也可能在持锁状态下同步写盘，进一步放大延迟。

### 3. VirtIO 请求是同步且自旋等待的

每个块设备由一个 `Mutex<VirtIOBlk>` 包起来；历史代码位于
`os/src/drivers/block/virtio_blk.rs`。

驱动提交请求后执行：

```rust
while !self.can_pop() {
    spin_loop();
}
```

历史循环可在 `4efa921d^` 版本的
`vendor/virtio-drivers-pci/src/queue.rs` 中复核。

这带来三个问题：

- 当前 hart 在设备完成前持续占用 CPU。
- 同一设备无法有效保留多个 outstanding requests，VirtIO 队列深度基本没有利用起来。
- 如果设备完成丢失或队列状态异常，只会打印 `virtqueue stuck`，没有超时退出；而上层可能还持有 `EXT4_LOCK`。

于是一次异常 I/O 可能产生这样的连锁反应：

```text
VirtIO 请求没有及时完成
        ↓
持锁任务一直自旋
        ↓
EXT4_LOCK 一直不释放
        ↓
所有 create/read/stat/readdir 排队
        ↓
整个文件系统表现为“卡死”
```

### 4. 为什么 Linux 没有这么严重

Linux 通常采用：

- inode、目录、页等更细粒度的锁；
- 文件读写优先进入统一 page cache；
- 脏页由后台 writeback 异步写盘；
- 块请求通过 bio/request queue 异步提交；
- 同时保留多个请求，完成后由中断唤醒等待任务。

Linux 也有日志、目录和分配器上的串行点，但不会用一把锁覆盖所有文件、所有操作以及完整的磁盘等待时间。

### 5. 这和目前三个 CAgent 卡住有什么关系

最新卡住的是 `fs-create`、`fs-directory`、`fs-search`，与这条路径高度相关。但目前只能说“结构上可疑”，还不能直接认定全局锁就是根因。

需要抓取：

- 每个 hart 当前调用栈；
- `EXT4_LOCK` 的持有者、操作类型和持锁时间；
- VirtIO 的请求 token、avail/used index；
- 块缓存管理器是否正持锁等待 I/O。

这样才能区分：

- 单纯串行化导致测试极慢；
- 锁顺序形成死锁；
- VirtIO 完成丢失；
- 块缓存淘汰或同步路径卡住。

### 推荐的改造顺序

1. 先给三层锁增加等待时间、持有时间和当前操作统计。
2. 缓存未命中时释放全局缓存管理器锁，用“正在加载”状态避免重复读。
3. 利用已有的 `read_blocks_nb/write_blocks_nb` 接口实现异步请求和睡眠唤醒。
4. 将 `EXT4_LOCK` 拆为文件系统、目录、inode、块分配等不同锁域。
5. 最终接入统一 page cache 和后台 writeback。

不能直接删除 `EXT4_LOCK`：它目前也在保护尚未线程安全的 ext4 内部状态。直接删掉很可能把性能瓶颈变成元数据损坏。正确方向是先明确共享状态和锁顺序，再逐步细化锁粒度。
