# fix-per-day 文档改写风格规范

参照样例（必须先读）：
- `7-30-ext4.md`（原始范式）
- `7.31-ext4-virtio-concurrency.md`（已按规范改写完成。重点参考主干五节的写法，
  以及 `## 背景知识` 一节的深度和口吻——那是给本科生看的标准样板）

## 一、总体结构

```md
# <日期> <一句话说清改了什么>

## 问题概述

## 背景知识

## 如何发现

## 怎么解决

## 对应提交

## 对比提升

以下是 AI 的具体分析，作为存档。

---

## 历史分析背景

<原文的全部细节，原样保留>
```

要求：

1. `问题概述`、`如何发现`、`怎么解决`、`对应提交`、`对比提升` 五节要短，合起来
   控制在 100 行以内。读者只看这五节就能明白「什么问题、怎么发现的、怎么修的、
   修了多少」。
2. `背景知识` 一节不受这个限制，见第四部分。涉及的机制如果本科 OS 课不会讲，
   就必须写这一节。
3. 原文的长篇细节（设计推导、逐条不变量、完整测试数据、复现命令、SHA-256、
   后续工作）一律搬到 `---` 之后作为存档，不要删除任何数据、提交号、哈希、命令。
4. `---` 之前紧接一行 `以下是 AI 的具体分析，作为存档。`
5. `---` 之后第一节固定为 `## 历史分析背景`，两三句说明这个问题当时为什么难改、
   涉及哪些子系统、为什么保留长篇分析。
6. 如果原文本身就没有长附录（全文很短），则不必强行制造附录。

## 二、各节写什么

- `## 问题概述`：现象 + 根因一句话。如果涉及调用链、锁层次、串行路径，画一张
  ```text``` ASCII 图，比文字更直观。已在别的文档分析过的，用一句话指过去
  （例：「这三层锁是怎么叠起来的，`7-30-ext4.md` 已经写过，本文是对应的修改」），
  不要重复。
- `## 如何发现`：说清发现手段。perf 采样、iozone/BuildStorm 日志、串口输出、
  对照 Linux 哪个文件哪个函数、AI 审查代码发现。有命令就贴命令，有日志路径就贴路径。
  如果原文没写清楚，就按原文能推出的事实写，不要编造。
- `## 怎么解决`：分层/分点写，每点一个粗体小标题。只贴最关键的代码片段（结构体、
  枚举、几行核心逻辑），代码注释里点出关键约束。末尾一段说明 Linux 是怎么做的、
  本项目做了哪些简化、哪几条与 Linux 一致 —— 要诚实交代边界。
- `## 对应提交`：短 hash + 提交标题。文档提交和实现提交分开列。纯诊断文档明说
  「本文是诊断记录，没有实现提交」。
- `## 对比提升`：数字优先。多组数据用表格，分成「提升项 / 持平项 / 退化项」。
  必须解释为什么某些指标退化或没变，指出下一个瓶颈在哪。没有跑的测试要明说没跑。

## 三、语言要求（最重要）

1. **不要用抽象名词堆叠**。禁用或改写以下这类词：
   - 结构性成因 → 「这几层锁是怎么叠起来的」
   - 全局等待点 → 「所有人都要抢的锁」
   - 多在途请求 → 「队列里同时挂多个请求，不必一个做完再发下一个」
   - 有界短轮询 / 无界忙等 → 「先轮询固定次数，次数用完就让出 CPU，不会一直空转」
   - 两阶段状态机 → 「两步走」
   - 稳定键 → 「这个编号不会随路径写法或对象重建而变」
   - 不变量清单 → 「需要保证的条件清单」
   - 单次加载 / single-flight → 「只有第一个发现缺失的任务去读，其他任务等结果」
   - 生命周期语义、协议约束、设计空间、收敛、对齐、赋能、闭环 → 一律换成动词短语
2. 技术专有名词保留英文：inode、dentry、page cache、TLB、ASID、extent、writeback、
   folio、bio、used ring、descriptor、futex、mmap 等。但**首次出现时用括号解释一句**
   （例：「generation（每次写入递增的版本号）」）。
3. 句子短，陈述式。不用感叹号，不用「显著地」「极大地」「完美」「优雅」这类评价词。
   不写「值得注意的是」「不难发现」「众所周知」。
4. 对已有实现给公允评价：既指出不足，也承认它做对了什么。
5. 承认不确定：没验证的说没验证，没跑的测试说没跑，退化的指标不掩盖。

## 四、必须补充的背景知识（重点要求）

**读者设定**：只上过一门本科操作系统课的大学生。他们知道进程、线程、虚拟内存、
页表、文件系统、锁这些基本概念，但**没有**读过 Linux 源码，不知道 folio、dentry、
blk-mq、ASID、STLB、RCU 这些具体机制，也不了解本项目的代码结构。

因此每篇文档都要有足够的背景铺垫，让这样的读者能读懂。具体做法：

1. 在 `## 问题概述` 之后、`## 如何发现` 之前，插入一节
   `## 背景知识`（如果这篇涉及的机制读者肯定不熟）。
   篇幅可以到 30–80 行，宁多勿少。讲清三件事：
   - 这个机制是干什么用的，解决什么问题；
   - 它在教科书里对应哪个概念（帮读者搭桥，例：「dentry cache 就是课上讲的
     『目录项缓存』，作用是避免每次开文件都去磁盘上一级一级查目录」）；
   - 它内部大致怎么工作，配 ASCII 图或小段伪代码。
2. 讲机制时**先给类比或直观图，再给术语**。例如先说「TLB 就是页表的缓存，
   查地址时先问它」，再引入 STLB/MTLB 这些名字。
3. 每个英文术语第一次出现时给中文解释 + 一句作用说明。
4. 主干里出现的代码片段，要说明每个关键字段是干什么的，不能只贴代码。
5. 附录（`---` 之后）保持原文的技术密度，不必为初学者改写。

可补充的知识点举例（有相关的就写，写不确定的就不写）：

- **perf 与 perf map 原理**：perf 是采样式 profiler。它让硬件性能计数器
  （PMU）每计满 N 个周期就产生一次中断，或者用定时中断，在中断里记录当前的
  PC（程序计数器）和调用栈。跑一段时间后统计哪个地址出现次数最多，就知道时间
  花在哪。因为记下来的是**地址**，要变成函数名需要符号表；对于运行时才确定地址
  的代码（JIT 编译的代码、裸机内核被加载到某个基址），perf 会去读
  `/tmp/perf-<pid>.map` 这种文本文件，每行是「起始地址 长度 符号名」，据此把
  地址回填成名字。没有这个映射，火焰图上就只剩一串十六进制地址。要说明采样式
  profiler 只给统计分布，不给精确调用次数，所以它能指出热点但不能证明因果。
- **LoongArch 的两级 TLB**：LoongArch 的 TLB 分成两块，查找时并行查两块。
  - STLB：按一种固定页大小组织，组相联，表项多，用来装绝大多数普通页映射；
  - MTLB：全相联，每一项可以自带页大小，用来装大页和特殊映射。
  一次取地址两块同时查，命中任意一块即可。这个设计的后果是：刷新 TLB 时要考虑
  两块都可能有残留项。`invtlb` 指令通过 op 编码选择刷新粒度——可以按 ASID
  （地址空间编号，用来区分不同进程的映射，避免切进程时全刷）刷、按虚地址刷、
  或者只刷/只保留全局项。另外 LoongArch 有 DMW（直接映射窗口），一段虚地址
  不经过页表直接对应物理地址，内核可以用它访问物理内存，这段地址不占 TLB。
  还有 `tlbsrch`（查）、`tlbrd`（读表项）、`tlbwr`（写当前项）、`tlbfill`
  （填一项，硬件选位置）几条指令分工不同，写错会刷掉别的表项。
- **RISC-V 的 TLB 刷新**：`sfence.vma` 有四种形式，可以带虚地址、带 ASID、
  或者两个都不带（全刷）。跨核刷新没有硬件广播指令，要靠软件给别的核发核间
  中断，在 SBI 上就是一次 remote fence 调用，代价远高于本核一条指令。所以
  「什么时候可以只刷本核」很值钱：把一个**原本无效**的页表项改成有效时，别的核
  的 TLB 里不可能缓存过这个映射（它们只可能缓存过「无效」，而规范允许硬件不缓存
  无效项），所以只需本核刷新；反之，把有效项改成无效或换指向，就必须通知所有
  可能用过它的核。取指令还要额外考虑 i-cache 与 fence.i。
- **Linux 里的相关机制**（用到时解释）：`i_rwsem` 是每个 inode 一把读写锁；
  `try_to_wake_up()` 用 `pi_lock` 和 `on_cpu` 标志保证一个任务不会同时在两个核上
  跑；blk-mq 轮询有次数预算并在需要调度时退出；buddy allocator 靠 pfn 异或
  order 找到「伙伴块」，检查伙伴也空闲就合并成更大块；dentry cache 用 `d_seq`
  序号让查找过程不加锁也能发现自己读到了正在被改的数据；slab 给每个 CPU 一个
  独立的空闲链表，绝大多数分配不用抢全局锁。

补充知识要落在「为什么这个机制导致了本文的问题，或者为什么方案必须这么写」上，
不要写成脱离上下文的教科书节选。

## 五、不要做的事

- 不删任何提交号、SHA-256、日志路径、命令、测试数字。
- 不把没跑过的测试写成通过。
- 不改动文档以外的任何文件。
- 不新建额外的 markdown 文件。
- 不修改文件名。
